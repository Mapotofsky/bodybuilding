# P4.1 需求文档：竞品补强与界面优化

> 对应阶段：P5 AI 前置阶段，基于竞品分析进行功能补强与界面优化  
> 状态：规划中，尚未实现  
> 上游依据：`ref-fig/逐图功能分析与IronLog对比.md`、`概要设计文档.md`、P0-P5 详细设计文档  
> 目标读者：后续详细设计编写者、实现者和验收者

---

## 1. 背景与目标

竞品截图分析显示，IronLog 当前训练记录基础较稳，但在训练回顾、统计复盘、动作详情表达、身体数据追踪、RM 能力记录、分享和“我的”页信息架构上仍明显偏基础。下一阶段应优先补齐这些高频体验能力，让本地单人版在无账号、无服务器、WebDAV 可选同步的前提下，具备更完整的训练复盘和个人数据管理体验。

本阶段目标：

1. 将日历从“训练点状记录”升级为可直接阅读训练部位、模板和统计入口的训练日历模块。
2. 在日历模块内组织“日历 / 统计”视图；统计视图内提供周 / 月 / 年周期切换，并把年度复盘作为 year 周期下的报告化呈现。
3. 增强动作详情：肌群可视化、动作成绩记录、RM 估算和趋势基础能力。
4. 将身高、体重等身体指标从 ProfileDoc 单值资料中拆出，形成支持历史变化与趋势统计的独立模块。
5. 重构“我的”页入口，把个人资料、应用设置、同步备份、小工具、身体数据等分区。
6. 新增日期/时间段备注，用于解释训练环境、器械、通勤、压力等上下文变化。
7. 增加本地生成分享图能力，训练分享只以图片形式交付。
8. 为 WebDAV 多人共享保留远期模型思考，但不改变当前本地单人版目标。

P5 AI 智能体与安全在本阶段之后再考虑。本阶段不得把 AI、provider、API key、联网 agent 或候选计划导入作为实现前提。

## 2. 下一阶段功能范围

### 2.1 训练日历模块

- CalendarPage 向竞品训练日历看齐：日历单元格增高，直接显示训练部位短标签。
- 日历页定位为实际训练总览；所有实际训练记录默认可见，不提供部位筛选，也不因部位状态提示隐藏训练记录。
- 日历格内显示实际训练的部位短标签；部位标签直接使用 `ExerciseDoc.category` 归类，不从 `MuscleGroupId` 推导，不同 category 使用稳定颜色区分。
- 部位距上次训练的状态，如“今天”“3 天”等，如果保留，只作为轻量状态提示或图例，不改变日历内容。
- 顶部组织“日历 / 统计”视图；统计视图内再提供周 / 月 / 年周期切换。
- 日历视图继续支持日期选择、查看当日训练、从选中日期新建训练。
- 正常情况下一天通常只有一个计划/模板，但日历格仍展示训练主要 category。日历格规则不得改变选中日期下方训练记录卡片的既有展示。多次训练或多个 category 时允许显示 2-3 个短标签并折叠剩余项。
- CalendarPage 不展示未来计划条目，也不承载未来排期；首页可以显示一个“下次训练”摘要，该摘要只取未来 14 天内最近一个未完成计划候选。

### 2.2 统计与周期复盘视图

- 统计模块提供周 / 月 / 年周期切换，未来可扩展全部或自定义周期。
- 首版只支持周 / 月 / 年，不实现全部或自定义周期。周为周一到周日，月为自然月，年为自然年；所有统计基于 `WorkoutDoc.date`，不从 `startTime` 推导归属日期。
- 周期对比统一使用上一自然周期作为基准：本周 vs 上周、本月 vs 上月、今年 vs 去年；不做过去 7 天等滚动窗口对比，也不做自定义周期对比。
- 当前自然周期未结束时仍与上一完整自然周期对比，UI 应标注“本周期截至今日”或等价提示，避免把未完成周期误读为完整周期。
- 年度复盘不是独立数据模块或独立数据真源，而是统计模块 `year` 周期下的报告化呈现；未来月度复盘、季度复盘也应复用同一统计 service。
- 统计模块采用分层页面形态：`week` / `month` 是统计仪表盘，重点展示当前周期 KPI、上一自然周期差值、趋势图、肌群分布、身体指标摘要或小趋势，以及 PR/RM 全局入口；`year` 是报告化复盘，重点展示年度总览、按月图表、年度热力图、肌群覆盖、身体指标年度变化和 PR/RM 全局摘要。
- `week` / `month` / `year` 共享同一套统计 service/core 口径；页面形态不同不等于新增独立真源，也不持久化复盘快照。
- 周/月统计至少覆盖训练次数、总组数、训练时长、总容量、容量曲线、细粒度肌群分布、周期差值和周期打卡视图。
- 容量曲线使用统一训练容量统计口径，页面不得自行重复计算 `weight * reps`。`week` 按日聚合显示 7 个自然日；`month` 按日聚合显示当月每天，相邻月日期不计入 month 容量曲线；无训练日期显示 0，不做插值。
- `year` 容量曲线采用双层趋势：主线为粗折线，展示各月日均容量，口径为当月总容量 / 当月自然天数；背景线为淡色平滑曲线，展示原始每日容量的固定 7 日滑动平均。背景线不显示逐日数据点，不提供点位查看，只用于补足全年连续变化感。
- `year` 容量主线 tooltip 展示月份、月总容量、日均容量和训练天数。原始每日容量仍来自 `WorkoutDoc.date` 和统一容量统计口径；7 日滑动平均只是展示层派生，不改变统计真值，不参与 KPI、周期差值或 PR/RM 计算。
- 训练时长首版使用 `WorkoutDoc.endTime - WorkoutDoc.startTime`；缺少完整起止时间的训练不计入时长图表，但仍计入训练次数、组数和容量。
- 周期差值首版只覆盖训练次数、总组数、总容量；PR/RM 周期对比由 P7 定义，统计与周期复盘视图只消费全局摘要。
- 周期打卡视图按周期分层呈现：`week` 不做热力图，只做 7 天横向打卡条或小型日历条；`month` 做自然月内日历打卡图，相邻月日期只作空白占位且不计入本月统计；`year` 做全年打卡热力图，用于年度复盘中的训练频率与连续性阅读，移动端应缩小强度格并按月分行。
- 所有周期的打卡强度统一按当天训练次数分档：0 次为空白，1 次为低强度，2 次为中强度，3 次及以上为高强度；不按容量、组数或训练时长分档。
- year 周期报告化呈现至少覆盖年度总览、最长连续、总容量、训练/休息天数、细粒度肌群或部位覆盖、PR/RM 全局摘要、锻炼时间按月柱状图、年度打卡热力图、训练天数与休息天数汇总。
- 统计与周期复盘视图应包含丰富聚合图表，例如训练次数对比、组数对比、训练时长对比、容量曲线、细粒度肌群分布、周期差值、周期打卡视图、PR/RM 全局摘要。
- PR/RM 在统计与周期复盘视图中只展示全局摘要和入口，不展开 RM 公式明细。
- PR/RM 全局摘要首版展示三块：本周期新增记录数、Top 提升动作、最近刷新记录。本周期新增记录数拆分真实 PR 数和基于 RPE 修正 RM 刷新数；Top 提升动作最多 3 个，按本周期刷新幅度排序；最近刷新记录最多 5 条，按达成时间倒序。
- Top 提升动作的刷新幅度按同一动作、同一指标内的相对提升比例排序：`(newValue - previousBestValue) / previousBestValue`。`previousBestValue` 由 service 基于当前刷新事件之前的同指标历史最佳派生，不作为新增持久化字段；首次记录或无法派生旧值的记录不进入 Top 提升，只计入新增记录数和最近刷新记录。
- 不同指标之间不做复杂统一换算；按受控记录方式和指标注册表生成候选，例如最大重量、次数、容量、距离负载、持续负载、单位时间负载和 RPE 修正 RM。重量 PR 与 RM 使用输入重量换算后的 kg，聚合负载由核心双倍率口径计算。Top 提升动作最终优先选择相对提升比例最高的可比较记录，展示动作名、指标名、旧值、新值和提升百分比。
- PR/RM 全局摘要只读消费 P7 的 `ExercisePerformanceRecordDoc`，统计页不重新生成成绩事件。统计页文案统一使用“基于 RPE 修正 RM”摘要；点击记录进入动作详情或来源训练详情；本周期没有刷新时显示空态，不用历史最佳记录填充。
- 统计视图可以只读展示身体指标派生结果，但不成为身体数据管理页，也不改变训练统计口径。
- week / month 统计仪表盘展示本周期内有有效记录的全部身体指标维度的小趋势或周期变化，不固定为体重、体脂、腰围三项；无本周期记录的维度不展示。若上一自然周期没有对应指标记录，只展示当前周期可用值，不用箭头暗示变化。
- year 周期报告化复盘展示本年度内有有效记录的全部身体指标维度的年度变化摘要，例如年初到年末变化、最高/最低值和关键趋势；稀疏记录不足时显示空态、单点状态或可用记录范围，不补点推断。
- 身体指标展示统一消费 `BodyMetricDoc` 派生结果；当前值仍按各指标最新非空、非未来、非 tombstone 记录派生。统计页身体指标栏中，左右成对围度应合并在同一行展示左右值；若在趋势图中展示该成对指标，则同图双序列展示并和身体数据页保持一致。
- 身体指标展示不参与训练次数、组数、训练时长、容量、PR/RM 的计算；新增、编辑、删除、历史列表和单条测量备注仍归 P6 身体数据模块。
- 统计页的肌群分布使用 `primaryMuscleGroupIds` / `secondaryMuscleGroupIds` 做细粒度分析；CalendarPage 的短标签才使用 `ExerciseDoc.category` 做总览。
- 细粒度肌群分布使用工作组数加权，排除 `isWarmup=true`；主目标肌群权重为 `1.0`，次要目标肌群权重为 `0.5`。缺失目标肌群的动作不参与肌群分布，也不从 category 兜底推断。
- 细粒度肌群分布的计算覆盖全部有效肌群；图表默认按当前周期加权工作组贡献降序展示 Top 8，其余合并为“其他”。详情弹层或列表可展示完整肌群排名，不能因为图表折叠丢弃底层计算结果。
- 统计结果优先由本地 WorkoutDoc、ExerciseDoc、TemplateDoc、BodyMetricDoc 和后续持久化成绩记录派生，其中 BodyMetricDoc 只用于身体指标展示；不持久化统计或复盘快照。
- 统计页面可显示日期/时间段备注标记，帮助解释曲线变化。

### 2.3 动作详情增强

- 增加肌群可视化，基于 `primaryMuscleGroupIds` 与 `secondaryMuscleGroupIds` 着色。
- 主目标肌群使用更深的强调色，次要目标肌群使用较浅色。
- 媒体内容暂不作为优先项：视频、GIF、器械图片可以后置，肌群图不应被媒体资源阻塞。
- 增加动作成绩记录区，展示真实记录和 RM 估算结果。
- 保留现有实时统计逻辑，并提供手动重算/重置按钮，用历史 WorkoutDoc 重建持久化动作成绩记录。
- 动作详情页负责回答“这个动作我练得怎么样”，展示真实 PR、基于 RPE 修正的 RM 摘要、记录来源、周期对比、最近刷新记录和动作级趋势图表。
- 动作详情页的图表能力参考竞品“图表”tab：单次训练容量趋势、工作组数趋势、最大重量趋势、基于 RPE 修正的 RM 均值趋势、年份 / 全部切换、数据点跳转来源训练。
- 动作详情页不承担公式教学和手动计算，不展开 RM 公式说明内容。

### 2.4 RM 计算与动作成绩记录

- RM 计算是必要训练能力，不依赖 AI，也不等同于训练计划自动写入。
- RM 计算器可作为“小工具”独立使用。
- 小工具页是工具集合入口，不直接等同于 RM 计算器；首版至少提供 RM 计算器入口，并可列出未实现的力量训练 / 有氧训练 RPE 说明页占位。
- RM 计算器页负责手动输入重量、次数、RPE，展示 Epley / Brzycki / Lombardi / Wathen 明细和均值；计算器已同时展示四个公式，不额外展示范围或标准差说明。
- RM 计算器页负责展示以 `effectiveReps` 为 x 轴、`1RM / 重量` 为 y 轴的四公式倍率曲线，并解释具体公式和 `RPE -> RIR -> effectiveReps`。
- 训练结束后，可基于每个动作的真实 PR，以及记录了 RPE 的普通负重次数组自动更新个人动作成绩记录。
- 没有 `WorkoutSetDoc.rpe` 的普通负重次数组不生成 RM 估算事件，只保留真实 PR，例如最大重量、最大次数、最大单组容量和最大训练容量。
- RM 估算首版统一为“基于 RPE 修正的估算 RM”：使用现有 `WorkoutSetDoc.rpe` 派生计算概念 `RIR = 10 - RPE`，再计算 `effectiveReps = reps + (10 - rpe)`；不再另算一套基于原始 reps 的普通 RM。
- reps 和 `effectiveReps` 都必须在 `1..12`；任一超出范围则不生成 RM 估算事件。
- 首版 RM 公式固定为 Epley、Brzycki、Lombardi、Wathen；四个公式均使用 `effectiveReps`，公式结果独立保存并同步更新。
- RM 计算器默认展示四个公式结果与均值，不额外展示范围或标准差；没有 RPE 时显示“未记录 RPE，未生成 RM 估算”。
- RM 刷新事件以四公式均值作为主比较口径，并保存四公式明细、均值、标准差或范围；候选并列时依次按均值、实际重量、原始 reps、日期较新排序。
- RIR 只作为计算概念和 UI 说明，不进入 `WorkoutSetDoc`、成绩事件或其他持久化文档。力量训练 RPE 按“还能做几次”解释；有氧训练 RPE 按主观感受和心率分区解释，不参与 RM 估算。
- RM 计算器页展示具体 RM 公式与倍率曲线；力量训练 / 有氧训练 RPE 说明页作为小工具集合中的后续工具，不作为 RM 计算器首版完成条件。
- 动作成绩记录首版只保存刷新历史最佳的事件，不保存每次训练的候选点；趋势曲线从 WorkoutDoc 派生。
- 成绩事件由训练 service 在训练结束保存、已完成训练编辑保存、已完成训练 tombstone 删除后统一调度生成、清理或重算；未结束草稿不生成成绩事件，也不触发成绩事件重算。用户不手动新增或编辑成绩事件，只能查看来源、手动重算、清空并重建。
- PR/RM 成绩事件排除 `isWarmup=true` 的组；训练总容量仍遵守 P0 现有口径。
- PR 按六种受控记录方式及成绩方向生成，RM 只覆盖普通负重次数模式。负重次数、辅助重量、仅次数、保持时间、距离/时间、负重时间和负重距离分别使用 P7 注册的指标；页面不得自行推导或假定所有数值越大越好。

### 2.5 身体数据独立模块

- 身体数据不应继续作为 ProfileDoc 的单值附属字段扩展。
- 新增独立身体数据模块，支持身高、体重、体脂、围度、左右侧围度、记录日期和备注。
- 支持当前值视图、历史变化、趋势图、身体指标统计和固定范围切换。
- `BodyMetricDoc` 是身体指标唯一真源；字段包含 `heightCm`、`weightKg`、`bodyFatPercent`、`measurementsCm`、`recordedAt`、`note`。
- `BodyMetricDoc.weightKg` 按 kg 作为规范持久化单位；体重输入和展示复用全局 `SettingsDoc.weightUnit` 在 kg/lb 间转换。`heightCm` 和 `measurementsCm` 首版固定使用 cm，不跟随 `weightUnit`。
- `recordedAt` 必须使用 `ISODateTime`，不能只保存日期；UI 可以按日期分组展示，但排序、当前值派生和“当天最后一条非空记录”判断必须使用完整时间。
- `recordedAt` 是身体测量事实发生时间，必须 `<= now`；允许补录过去时间，不允许写入未来时间。
- `BodyMetricDoc` 是稀疏测量记录，不是强制完整快照；创建记录时允许只写入本次确认或修改的部分指标。
- `BodyMetricDoc` 首版支持新增、编辑和 tombstone 删除单条历史记录。编辑只修改该条记录本身，不把旧指标补全成完整快照；删除后当前值、趋势图和统计从剩余有效记录重新派生。
- `BodyMetricDoc` 至少要有一个身体指标非 `null`；`note` 只作为本次身体测量备注，例如“晨起空腹”“训练后测量”，不允许创建只有 `note` 而无任何测量指标的身体记录。
- `BodyMetricDoc` 持久化 JSON 使用固定字段，未测量字段写为 `null`，不通过省略字段表达未测量。`null` 只表示“本条记录未测量该指标”，不表示清空该指标的历史当前值。
- `measurementsCm` 使用固定围度键，每个围度未测量时同样写为 `null`，不使用自由键值对象；首版不支持自定义围度项，也不新增 `customMeasurementsCm` 或动态字段。
- UI 可以用上次值预填表单，但预填值不自动保存为本次测量事实；只有用户本次确认或修改的字段才写入 `BodyMetricDoc`，未确认字段不保存为本次测量值。
- `BodyMetricDoc` 不新增 `confirmedFields` 或类似字段集合；持久化层以字段值是否为非 `null` 表达本次是否测量该指标，UI 可在提交前内部维护“本次确认/修改字段集合”。
- 当前身高、当前体重、当前体脂、当前围度、趋势图和身体指标统计均按“每个指标各自取最新非空记录”派生；派生时默认排除 tombstone 和未来时间记录。
- 身体数据当前值摘要按指标分组展示：基础指标包含身高、体重、体脂；围度指标单独分区。左右成对围度在同一行展示左右最新值和差值。
- ProfileDoc 保留为本地个人资料文档，可作为未来账号或共享资料的本地映射预留；当前版本不实现账号、登录、用户权限或多人身份体系。
- ProfileDoc 首版建议只保留 `nickname`、`avatarUrl`、`gender`、`birthDate`，不承载身体数据历史。
- 首版身体数据从“我的”入口进入，不进入底部导航。
- `BodyMetricDoc` 允许一天多条记录；日粒度趋势按具体指标独立聚合，默认取当天该指标最后一条非空记录。例如同一天早上记录体重、晚上只记录腰围，则当天体重取早上的最后非空体重，腰围取晚上的最后非空腰围；不得要求同一条 `BodyMetricDoc` 同时包含所有趋势点。
- 身体数据趋势图首版提供固定范围切换：`30天`、`90天`、`1年`、`全部`；不实现自定义区间、复杂时间粒度切换或额外聚合模式。
- 身体数据趋势图默认按单指标查看；但左右成对围度指标必须支持同图对比，例如左/右上臂、左/右前臂、左/右大腿、左/右小腿在同一张图中展示两条趋势线。
- P6 实施时直接用 `BodyMetricDoc` 替换旧 `ProfileDoc.height` / `ProfileDoc.weight` 身体数据模型；从后续模型与 UI 移除 `ProfileDoc.height` 和 `ProfileDoc.weight`，不编写迁移，不在读取层兼容旧字段，不将旧字段作为初始身体记录候选。开发/测试数据清空后按新模型重建。

### 2.6 “我的”页拆分

- 当前 ProfilePage 中主题、重量单位、个人资料、同步入口混在一起，信息架构不够直觉。
- “我的”页应变为入口页，而不是所有配置都在同一个个人资料表单中编辑。
- 建议入口包括：个人资料、应用设置、同步备份、小工具、身体数据、分享/导出。首版不设置“关于”子页。
- 个人资料编辑页不再展示或编辑身高、体重；如“我的”页需要展示当前身高或体重，必须读取 `BodyMetricDoc` 中对应指标的最新非空记录。
- 主题设置、重量单位、默认显示偏好等应进入应用设置，不再混入个人资料。
- 首版应用设置只持久化 `themeId` 和 `weightUnit`；统计默认周期、分享图默认样式等偏好不在首版新增持久化字段，除非对应功能实现前另行决策。
- `weightUnit` 只影响重量类输入和展示，包括训练重量、RM/PR 重量和身体体重；不影响身高、围度或距离单位。
- RM 计算器入口为“我的 -> 小工具 -> RM 计算器”；动作详情页如提供跳转，只能作为 RM 摘要区域的辅助入口，不从训练创建流程强插入口。

### 2.7 日期/时间段备注

- 新增日期/时间段备注能力，用于记录训练背景变化。
- 典型例子：从某天开始跑步通勤、某段时间更换器械品牌、某阶段压力或睡眠变化、某健身房器械角度不同导致体感重量变化。
- `TimelineNoteDoc` 定位为跨训练、统计、动作趋势和身体趋势的时间范围背景标记，不是训练备注、身体测量备注、日记流或普通备忘录。
- 三类备注边界必须清晰：`WorkoutDoc.note` 用于解释某一次训练；`BodyMetricDoc.note` 用于解释某一次身体测量；`TimelineNoteDoc` 用于解释某一天或某段时间的外部背景。
- 备注不直接改写训练记录、身体数据或成绩事件，不参与训练统计、身体统计或 PR/RM 计算口径；它只作为解释层在日历、统计、动作趋势或身体数据趋势中显示标记。
- 如果只是记录一段身体状态、训练背景或生活背景而没有身体测量值，应使用 `TimelineNoteDoc`，不创建 note-only 的 `BodyMetricDoc`。
- `TimelineNoteDoc` 首版以日期/时间段备注为主，支持可选 `workoutId`，不支持 `exerciseId` 或 `templateId` 关联。
- `TimelineNoteDoc` 首版只保留 `content`，不新增 `title`；日历或趋势图上的短摘要由 `content` 截断生成。
- `TimelineNoteDoc` 首版不新增 `category`、`type` 或标签字段；分类、筛选或搜索能力后续另行设计，不进入首版持久化模型。
- `TimelineNoteDoc` 表达日级或时间段背景，不是事件日志；`startDate` / `endDate` 使用 `ISODate`，不升级为时间戳。
- 时间范围明确区分 `rangeType: "single_day" | "date_range" | "open_ended"`；所有范围类型均要求 `startDate <= today`，禁止创建未来开始的 TimelineNote。`single_day` 要求 `endDate === startDate`，`date_range` 要求 `endDate >= startDate`，`open_ended` 要求 `endDate === null`。
- `date_range.endDate` 可以晚于今天，用于表达已开始且预计到某天结束的背景；查询和展示仍按 `queryEnd <= today` 裁剪，不在未来日期生成可见条目。
- 生效查询使用闭区间重叠口径：查询窗口为 `[queryStart, queryEnd]`，其中 `queryEnd` 最晚为 `today`；备注有效范围为 `[startDate, effectiveEndDate]`，`open_ended` 的 `effectiveEndDate` 为 `today`。满足 `note.startDate <= queryEnd && effectiveEndDate >= queryStart` 即为生效。
- 展示时再将生效备注裁剪到当前视图范围；`open_ended` 备注不向未来日期铺开。
- 允许多个 `TimelineNoteDoc` 在同一天同时生效，但语义是多个时间范围背景重叠，而不是鼓励同一天写多条日记；例如一个 `open_ended` 的“开始跑步通勤”和一个 `single_day` 的“昨晚睡眠差”可以同时覆盖同一天。
- `TimelineNoteDoc` 不做自动合并；自动合并会改变原始语义，合并、拆分、删除只能由用户显式操作。

### 2.8 本地分享图

- 新增本地生成分享图能力，训练分享只采用图片形式。
- 分享图首版只覆盖训练详情分享图，不覆盖身体数据分享图、统计/周期复盘分享图或动作详情分享图。
- 分享图首版只提供一个固定训练详情模板，不做多模板、主题包或模板编辑器。
- 分享图默认使用紧凑内容：日期、训练名称或模板名、总容量、训练时长、动作数、组数、主要 category 或肌群标签、备注摘要，以及每个动作的摘要行；默认不展开每一组明细。
- 分享图每个动作摘要行显示组数、最佳组和动作总容量，不展开复杂统计。
- 分享图提供运行时“显示明细”选项；开启后使用同一固定模板纵向扩展为长图，展示所有动作和所有训练组的组明细，例如重量、次数、RPE、休息等当前训练已有字段。该选项不设条数上限，不分页，不新增模板类型，也不保存为默认偏好。
- 若本次训练产生 PR/RM 刷新事件，分享图默认在训练摘要区显示轻量成绩摘要，例如“本次刷新 N 项记录”和最多 2-3 条动作名 + 指标摘要；不新增独立开关，不展示 RM 公式明细、公式教学或历史记录列表。
- 分享图中的备注摘要只读取 `WorkoutDoc.note`，不自动带入 `TimelineNoteDoc`。如后续需要展示当天背景标记，必须另行设计运行时选项。
- 训练详情分享图首版只包含训练摘要、动作摘要或明细、容量、主要 category 或肌群短标签、备注摘要和轻量 PR/RM 刷新摘要；短标签直接使用 `ExerciseDoc.category`，不从 `MuscleGroupId` 推导；不生成独立肌群图，不包含身高、体重、体脂或围度等身体数据，也不需要身体数据隐藏样式。
- 分享图首版只生成 PNG；固定宽度 1080px，高度随内容自适应。
- 分享图生成使用当前主题 token，不提供分享图主题选择，也不保存分享图样式偏好。
- 不上传分享图，不自动写入 WebDAV。
- 分享图预览页提供两个动作：保存图片、系统分享；不提供复制文字兜底。
- 分享图固定模板不显示昵称、头像、身高、体重、体脂或围度等个人资料和身体数据。
- 分享图主入口在训练详情页；训练结束后进入详情页再分享，不在 finish 阶段强制弹出。
- 正式训练分享只输出图片；“复制训练摘要”可以作为训练详情页普通工具动作保留，但不作为分享功能兜底。
- 分享图生成失败时使用 toast 提示并保留预览或重试入口，不创建训练、成绩、设置或同步相关业务记录。

### 2.9 WebDAV 多人共享远期预留

- 本阶段不引入账号、登录、服务端权限或实时多人协作。
- 可以在数据模型与同步文档中预留远期讨论：基于 WebDAV 目录或凭据权限实现“搭子”（只读）和“教练”（可读可写）等角色。
- 该预留不得改变当前本地单人版运行目标，也不得让页面或 core 依赖账号体系。

## 5. 对现有模块的影响分析

### 5.1 P0 核心训练

- RM 估算会读取组字段与历史负重口径；没有 rpe 的普通负重次数组只参与真实 PR，不生成 RM 估算事件。
- 训练完成、已完成训练编辑和已完成训练删除流程需要由训练 service 触发动作成绩记录生成、清理或重算，但不能破坏已有逐组保存和草稿恢复；页面不负责临时修补过期成绩事件。
- 分享图仍以 WorkoutDoc 为数据源，不改变训练聚合文档结构。
- 训练详情分享图默认读取本次 workout 产生的 `ExercisePerformanceRecordDoc` 刷新事件作为轻量 PR/RM 摘要来源，但只展示数量和少量动作指标摘要，不展开 RM 公式明细。
- 训练详情分享图中的备注摘要只使用 `WorkoutDoc.note`；`TimelineNoteDoc` 不作为分享图默认数据源。
- 日期/时间段备注不应写进 WorkoutDoc；`WorkoutDoc.note` 仍只解释单次训练，训练详情可只显示关联备注摘要。

### 5.2 P1 计划、模板、动作库与日历

- CalendarPage 从实际训练月历升级为训练日历模块，但仍只展示实际训练记录，不展示未来计划条目。
- 首页可以显示一个“下次训练”摘要，只取未来 14 天内最近一个未完成的 weekly/cyclic 计划候选；flexible 计划不生成该摘要，CalendarPage 不承载未来排期。
- 日历格内标签要根据实际训练动作的 `category` 推导，必须定义单日主要 category 的选择规则；CalendarPage 不使用训练关联模板、`primaryMuscleGroupIds` 或 `secondaryMuscleGroupIds` 推导日历格标签。
- 统计与周期复盘视图可以使用 `primaryMuscleGroupIds` / `secondaryMuscleGroupIds` 统计细粒度肌群分布；不得把 CalendarPage 的 category 总览口径误用为统计页的肌群分析口径。
- 动作详情新增肌群图、成绩记录和趋势入口；P1 需继续保证缺失数据时显示“暂无”，不从分类猜测目标肌群。
- 动作库列表是否展示成绩摘要需要另行决定，不能在列表层重复计算。

### 5.3 P2 本地文档存储与迁移

- 需要新增身体数据、动作成绩记录、时间段备注等持久化文档或分片。
- 需要定义这些新文档的 BaseDoc、schemaVersion、tombstone、migration、默认值、导入导出和 WebDAV 往返。
- ProfileDoc 保留为本地个人资料文档，可作为未来账号或共享资料的本地映射预留；当前开源单人版不实现账号、登录、用户权限或多人身份体系。
- ProfileDoc 首版建议只保留 `nickname`、`avatarUrl`、`gender`、`birthDate`；P6 的 schema 演进只初始化新 `BodyMetricDoc` 结构并规范 schemaVersion，不转换、不读取、不兜底旧 `ProfileDoc.height` / `ProfileDoc.weight`。
- SettingsDoc 可继续承载 themeId、weightUnit 等应用偏好，但 UI 入口应从个人资料中拆出。

### 5.4 P3 WebDAV 同步与 Android

- 新增文档分片必须进入 manifest shards，并遵守 tmp/MOVE、backup、LWW 和本机端点配置隔离规则。
- 身体数据、动作成绩记录和时间段备注属于可同步业务数据；分享图默认不是同步数据。
- WebDAV 多人共享只做远期预留；当前 syncService 不承担权限判断或角色管理。
- Android 360px/412px 下需要重点验证增高日历格、统计图和身体数据趋势图。

### 5.5 P4 主题系统与 UI 导航

- “我的”页拆分会改变导航下的入口结构，P4 需补充设置页、同步页、小工具页、身体数据页等入口视觉规则。
- 新统计图、周期复盘图表、肌群图和分享图必须使用语义 token 或主题变量，不应继续扩大硬编码 emerald/slate。
- 图表颜色要纳入主题 token，保证深浅主题可读。
- P4.1 新增页面必须使用语义类或 CSS 变量；P4.1 重构页面的改动区域和页面主框架必须同步迁移到语义 token，不得新增硬编码 Tailwind 颜色。
- 业务数据颜色允许存在，例如计划/模板自定义颜色、category 稳定色映射、肌群图色映射，但必须集中在 token 或映射表中，不得散落在 JSX。
- 日历 category 颜色使用集中业务色映射，不作为用户主题的完全重定义项，但必须保证各主题下可读。

### 5.6 P5 AI 智能体与安全

- P5 保持后置。本阶段产生的 RM、身体数据、备注、动作成绩记录等数据，将来可能成为 AI 可选输入，但本阶段不定义 AI 输入边界或发送规则。
- 在 P5 重启前，需要重新评估这些新增数据是否进入 AI 工作流，以及对应的用户确认和字段范围。

P0-P4 详细设计文档承载了当前代码事实和关键数据契约，例如 WorkoutDoc 聚合、模板过滤、DocumentStore/WebDAV、themeId、tombstone 和 migration。它们不能在新详细设计生成前直接归档或删除。

后续 session 必须按以下顺序操作：

1. 先生成或修订下一阶段详细设计文档，覆盖 P4.1 需求涉及的页面、服务、core、repository、migration、同步和验收契约。
2. 新详细设计必须显式继承仍有效的 P0-P4 当前事实；被替代的规则要标注替代关系，不能让读者需要同时猜测新旧文档优先级。
3. 确认新文档完整覆盖当前实现基线后，才能将 P0-P4 作为“已完成阶段基线/历史参考”移动到 `archive/design-baseline-v1/` 或类似目录。
4. 归档时必须同步更新 `概要设计文档.md`、`README.md`、运行/部署文档和文档索引，明确旧 P0-P4 不再作为新增功能的权威入口。
5. 归档不得改变代码行为，不得删除仍被当前实现依赖的契约说明；如新文档尚未覆盖某项事实，应保留旧文档原位置或在新文档中迁移该事实。

简言之：先用新详细设计接住当前事实和 P4.1 需求，再归档旧阶段文档；不得先归档再从零生成。

## 8. 数据模型影响

本节只定义模型影响方向，不替代后续详细设计的字段契约矩阵。

### 8.1 新增候选文档

- `BodyMetricDoc`：记录 `recordedAt`、`heightCm`、`weightKg`、`bodyFatPercent`、`measurementsCm`、`note` 等身体指标，其中 `recordedAt` 使用 `ISODateTime` 且必须 `<= now`；`weightKg` 使用 kg 持久化，展示和输入按 `SettingsDoc.weightUnit` 转换；`heightCm` 和 `measurementsCm` 固定使用 cm。首版使用静态文件 `body-metrics.json`，不按月分片。未测量字段在持久化 JSON 中保留固定字段并写为 `null`，导入导出、migration 和 WebDAV 往返不得把字段省略当成稳定契约。`measurementsCm` 固定键为 `neck`、`shoulder`、`chest`、`waist`、`hip`、`upperArmLeft`、`upperArmRight`、`forearmLeft`、`forearmRight`、`thighLeft`、`thighRight`、`calfLeft`、`calfRight`；未测量围度写 `null`；首版不保存自定义围度项。
- `ExercisePerformanceRecordDoc`：记录动作个人成绩刷新事件、真实 PR、基于 RPE 修正的各 RM 公式估算结果、来源 workout/set、更新时间和重算状态；首版按月分片，例如 `exercise-performance/YYYY-MM.json`。字段只保存 `exerciseId`、来源引用、指标类型、指标值、规范单位、达成时间和必要的 PR/RM 输入摘要，不保存动作名称、分类或肌群快照。
- `TimelineNoteDoc`：记录单日、固定时间段或持续中的时间范围背景标记，可选关联训练；首版只保存 `content`，不新增 `title`、`category`、`type` 或标签字段；`startDate` / `endDate` 使用 `ISODate`，不保存时间戳；所有范围类型禁止 `startDate > today`；首版使用静态文件 `timeline-notes.json`，不按月分片。
- 训练详情分享图首版不读取 `BodyMetricDoc`，不展示身高、体重、体脂或围度等身体数据；分享图只生成本地 PNG 文件，不作为业务文档持久化，不进入 manifest，不新增身体数据隐藏选项、`ShareImagePreferenceDoc` 或 Settings 子字段；如后续扩展身体数据分享图、分享图默认偏好或在训练分享图中引入身体数据，必须先进入字段契约矩阵单独设计。

### 8.2 现有文档调整

- ProfileDoc 不继续扩展为身体历史表；保留为本地个人资料文档和未来账号/共享资料的本地映射预留，首版建议只保留 `nickname`、`avatarUrl`、`gender`、`birthDate`。
- SettingsDoc 继续保存应用偏好，例如 weightUnit、themeId；设置入口从 ProfilePage 中拆出不等于改变 SettingsDoc 语义。`weightUnit` 是重量展示/输入偏好，不改变 `BodyMetricDoc.weightKg`、成绩事件 kg 规范单位或训练组原始记录解析规则。
- ExerciseDoc 可考虑新增器械、难度等轻量动作元数据，但视频/GIF 和器械图片不在本阶段优先范围。

### 8.3 派生与持久化边界

- 周/月/年统计、周期复盘视图和趋势图优先派生，不持久化统计或复盘快照；周期差值的基准由 service/core 统一计算为上一自然周期，页面不得自行切换为滚动窗口或自定义对比。
- 统计与周期复盘视图只读消费身体指标 service/core 派生结果；不得在统计页实现 `BodyMetricDoc` 新增、编辑、删除、历史列表管理或单条测量备注管理。
- 统计视图中的身体指标展示必须遵守 P6 稀疏测量模型：展示本周期有有效记录的全部指标维度，不补全快照、不插值、不复制旧值；左右成对围度沿用身体数据页双序列口径。
- 事实型数据默认不变量：记录时间字段不得写入未来时间；派生当前值、趋势、统计和成绩摘要时默认过滤 tombstone、未来记录和不满足字段约束的记录；这些校验应在 service/core 层落实，不只依赖 UI 控件。
- 身体指标当前值、趋势图和统计均从 `BodyMetricDoc` 历史记录按指标维度派生；当前值按每个指标各自取最新非空记录。“我的”页需要展示身高/体重时，也必须读取 `BodyMetricDoc`，不得读取旧 ProfileDoc 字段。
- `BodyMetricDoc` 更新和删除不得生成补偿记录或复制旧值；编辑后只重算受影响指标，tombstone 删除后按各指标上一条有效非空记录自然回退。
- 身体数据当前值摘要由 service 按指标分组派生；左右成对围度需要同时返回左值、右值、差值和各自来源记录时间，避免页面重复扫描历史记录。
- 身体数据 service 和 mapper 必须拒绝或忽略 `measurementsCm` 之外的自定义围度字段；后续如需扩展自定义围度，应另行设计字段契约和图表选择规则。
- 身体数据 service 负责体重 kg/lb 输入归一化和展示转换；页面不得直接把 lb 写入 `weightKg`，也不得让身高或围度跟随 `weightUnit` 切换单位。
- 身体数据趋势图按固定范围读取和展示历史记录，首版不提供自定义时间区间、周/月粒度聚合或插值补点。
- 趋势图不做跨单位多指标混画；左右成对围度属于同单位、同部位对照，应作为同一趋势图的双序列展示。
- 读取性能首版不是问题，不为了读取最新记录而把旧指标复制成新的测量事实；后续数据量变大时，可在 service 层增加派生快照或倒序扫描优化，但不得改变 `BodyMetricDoc` 的稀疏测量语义。
- RM/PR 这类用户期望保留并跨设备一致的动作成绩记录可以持久化。
- 持久化成绩记录必须保留实时重算路径，允许用户手动重建。
- `ExercisePerformanceRecordDoc` 以刷新事件列表为持久化真源，当前最佳、排行榜、周期对比由事件列表和 WorkoutDoc 派生。
- 成绩事件 ID 使用确定性生成，基于来源 workout、workoutExercise、set 或 workout 维度、metricType、formula 等要素；重复重算不得产生重复事件。
- 成绩事件引用来源应至少包含 `exerciseId`、`sourceWorkoutId`、`sourceWorkoutExerciseId`、`sourceSetId | null`、`metricType`、`value`、`unit`、`achievedAt`；RM 事件另存公式明细、均值、标准差或范围，真实 PR 事件保存必要输入摘要。
- 成绩事件用于排序、比较和同步一致性，持久化 `value` / `unit` 必须使用规范单位：重量类 PR/RM 为 `kg`，容量为 `kg_reps`，距离为 `m`，时长为 `sec`，速度为 `m_per_sec`，次数为 `reps`。展示时按当前 `SettingsDoc.weightUnit` 转换重量和容量；来源训练组的原始 `weight + unit` 仍从 WorkoutDoc 解析。
- 成绩事件不保存 `exerciseNameSnapshot`、`categorySnapshot`、肌群快照等展示字段；展示时通过 `ExerciseDoc` 和来源 WorkoutDoc 解析，避免动作名称、分类或肌群出现多套持久化真源。
- 已完成训练保存或编辑后，训练 service 触发该 workout 关联动作的成绩事件重算；已完成训练 tombstone 删除后，训练 service 触发相关动作重算并删除或失效由该 workout 产生的成绩事件。
- 动作详情页、统计与周期复盘视图只读取 service/core 派生结果，不直接过滤、隐藏、生成或修补过期成绩事件。统计与周期复盘视图的 PR/RM 全局摘要只读消费 `ExercisePerformanceRecordDoc`，只展示本周期新增记录数、Top 提升动作和最近刷新记录；Top 提升动作所需 `previousBestValue` 从历史成绩事件派生，不新增持久化字段；空态不使用历史最佳记录填充。
- 手动“重算全部成绩”作为维护工具，用于异常修复、模型升级或字段规则变化后的全量重建。
- `TimelineNoteDoc` 是背景解释层，不参与训练数据、身体数据或成绩事件的计算口径；同一天可有多条生效备注，但系统不自动合并。
- TimelineNote create/update service 必须校验 `startDate <= today`；未来计划、提醒或尚未开始的背景不应写入 `TimelineNoteDoc`。
- TimelineNote service 查询必须先把 `queryEnd` 裁剪到 `today`，再按闭区间重叠判断生效范围；不得为了持续中备注在未来日期生成可见条目。
- 新字段必须进入 P2 字段契约矩阵，标明页面、service、core、mapper、repository、migration 和同步状态。

## 9. UI/交互影响

- 日历单元格高度增加后，需要重新验证 360px 和 412px Android 宽度下的可读性与滚动行为。
- “日历 / 统计”视图切换和统计周期切换应保持位置稳定，不应让用户丢失当前月份或统计范围。
- 统计视图可展示身体指标摘要或小趋势，但只能作为只读模块出现；管理身体测量记录仍从 P6 身体数据页进入。
- 日历页不提供部位筛选；所有实际训练记录始终可见；颜色只用于区分部位和帮助快速阅读，不作为过滤交互。
- 一天有多个部位或多次训练时，显示 2-3 个短标签，超出折叠为 `+N`。
- 肌群可视化应使用真实开源或自制人体肌群图资产，不用占位图或文本替代。
- “我的”页应成为入口中心；个人资料编辑、应用设置、同步备份和身体数据分别进入独立页面。
- 身体数据页应提供历史记录列表或详情入口，支持编辑和删除单条 `BodyMetricDoc`；删除使用确认对话框并写 tombstone，不做默认硬删除。
- 身体数据页的当前值区域应分为基础指标和围度指标；左右成对围度使用同一行展示左右值与差值，缺失一侧时显示单侧值和空态。
- 身体数据页的体重输入和展示使用当前 `weightUnit`；身高和围度输入、展示固定为 cm。
- 身体数据趋势图首版只提供 `30天 / 90天 / 1年 / 全部` 范围切换；不同指标记录频率不一致时允许折线自然断点，不做自动插值；左右成对围度指标在同一张图中用两条线对比。
- RM 工具应支持独立输入、公式明细、倍率曲线和说明；动作详情页只展示动作记录、来源、周期对比和趋势，不承担公式教学。
- 分享图生成必须有预览、保存图片和系统分享入口；训练分享不提供非图片兜底；首版固定模板生成 1080px 宽 PNG，高度随内容自适应；默认展示训练摘要和动作摘要，不展开组明细；动作摘要行显示组数、最佳组和动作总容量；用户可用“显示明细”运行时选项生成包含所有动作和所有训练组明细的长图，不设条数上限、不分页；若本次训练产生 PR/RM 刷新事件，默认显示轻量成绩摘要但不展开 RM 公式细节，且不新增独立开关；备注摘要只取 `WorkoutDoc.note`，不自动带入 `TimelineNoteDoc`；短标签直接使用 `ExerciseDoc.category`；首版固定模板不显示昵称、头像、身高、体重、体脂或围度等个人资料和身体数据；生成失败时 toast 提示并保留预览或重试入口，不创建业务记录。
- 分享图首版入口和内容模板只服务训练详情页；身体数据、统计复盘和动作详情如需分享图，后续按各自页面数据源单独设计。
- 日期/时间段备注应在日历和趋势图上只显示轻量标记或数量，避免遮挡主要数据；详情弹层或列表页再列出该日期生效的备注内容。
- TimelineNote 首版不提供复杂分类、筛选或搜索入口；展示收敛为标记、数量、详情列表三层。

## 10. WebDAV/同步影响

- 新业务文档必须进入 manifest，并随 WebDAV 手动同步、backup、tmp/MOVE 和 LWW 合并往返。
- `body-metrics.json`、`timeline-notes.json` 和 `exercise-performance/YYYY-MM.json` 均属于业务文档，必须进入 DocumentStore export/import、manifest shards、SyncService merge 和 WebDAV 往返测试。
- 新文档不得保存 WebDAV URL、用户名、passwordRef、密码或未来 API key。
- 身体数据和时间段备注作为普通业务文档随 WebDAV 同步。
- 分享图默认只本地生成和保存，不进入 manifest；若未来支持同步分享图，必须另行定义资源路径、默认隐藏配置和清理策略。
- WebDAV 多人共享只作为远期模型预留。本阶段不得修改 SyncService 为角色权限系统，也不得承诺只读/可写共享已经可用。

## 11. 验收标准

本阶段实现完成后至少应满足：

1. 日历页能显示训练部位短标签，日历格高度足以容纳主要信息，360px/412px 无裁切。
2. 不同部位颜色稳定、可读；日历页不因部位状态提示隐藏任何实际训练记录。
3. “日历 / 统计”视图和统计周 / 月 / 年周期切换在同一模块内可用，统计范围和日期口径清晰。
4. 统计与周期复盘视图基于自然周 / 月 / 年和 `WorkoutDoc.date` 统计，不把相邻月网格日期计入本月统计；周期对比统一为本周 vs 上周、本月 vs 上月、今年 vs 去年，当前周期未结束时标注截至今日；week / month 采用统计仪表盘形态，year 采用报告化复盘形态；三者复用同一统计 service，不持久化复盘快照。
5. 统计与周期复盘视图包含聚合图表、身体指标只读摘要和 PR/RM 全局摘要入口，但不展开 RM 公式明细；PR/RM 全局摘要只读消费 `ExercisePerformanceRecordDoc`，展示本周期新增真实 PR 数和基于 RPE 修正 RM 刷新数、最多 3 个 Top 提升动作、最多 5 条最近刷新记录，记录可进入动作详情或来源训练详情，本周期没有刷新时显示空态且不用历史最佳记录填充；Top 提升动作按同一动作、同一指标内的相对提升比例排序，展示动作名、指标名、旧值、新值和提升百分比，首次记录或无法派生旧值的记录不进入 Top 提升；细粒度肌群分布计算覆盖全部有效肌群，图表默认展示 Top 8 + 其他，详情可查看完整排名；身体指标展示消费 `BodyMetricDoc` 派生结果，展示本周期有有效记录的全部指标维度，不固定为体重、体脂、腰围三项；左右成对围度在身体指标栏同一行展示，若展示趋势则同图双序列展示；不参与训练次数、组数、训练时长、容量或 PR/RM 计算，也不提供身体测量新增、编辑、删除或历史列表管理。
6. 容量曲线使用统一训练容量统计口径；week 按日显示 7 个自然日，month 按日显示当月每天且相邻月日期不计入曲线，无训练日期显示 0、不插值；year 使用月度日均容量主线和每日容量 7 日滑动平均背景线，主线 tooltip 展示月份、月总容量、日均容量和训练天数，背景线不显示逐日点位、不参与 KPI、周期差值或 PR/RM 计算。
7. 周期打卡视图按周期分层：week 使用 7 天横向打卡条或小型日历条，month 使用自然月内日历打卡图且相邻月日期只作占位、不计入本月统计，year 使用全年打卡热力图并在移动端按月分行缩小强度格；所有周期强度均按当天训练次数分档，0 次空白，1 次低强度，2 次中强度，3 次及以上高强度，不按容量、组数或时长分档。
8. 动作详情肌群图按主/次目标肌群 ID 正确着色，缺失时显示“暂无”或空态；动作详情展示单动作 PR/RM 摘要、来源、周期对比和趋势，不承担公式教学。
9. RM 计算使用明确公式和单位换算规则；只对普通负重次数模式中记录了 RPE 且 reps 与 effectiveReps 均在 `1..12` 的组生成基于 RPE 修正的 RM 估算，并使用输入重量换算后的 kg；不新增 RIR 持久化字段；公式明细和倍率曲线只在 RM 计算器页展开。
10. 动作成绩记录可持久化、可随 WebDAV 往返，并可通过手动重算从历史训练重建；重复重算不得产生重复成绩事件。
11. 身体数据独立于 ProfileDoc，可新增、编辑、tombstone 删除稀疏测量记录并查看趋势；`measurementsCm` 首版只支持固定围度键，不支持自定义围度项；`weightKg` 以 kg 持久化，体重输入和展示复用 `SettingsDoc.weightUnit` 转换，身高和围度固定 cm；当前值摘要按基础指标和围度指标分组，左右成对围度同一行展示左右最新值和差值；趋势图首版支持 `30天 / 90天 / 1年 / 全部` 固定范围切换，不做自定义区间或复杂粒度聚合；跨单位指标不混画，左右成对围度指标同图双序列对比；`BodyMetricDoc.recordedAt` 不允许未来时间；编辑不把旧指标补全成快照，删除后当前值和趋势按剩余有效记录回退；P6 直接替换旧 `ProfileDoc.height` / `ProfileDoc.weight` 身体数据模型，不做迁移或兼容读取；当前身高、体重、体脂和围度按各指标最新非空、非未来、非 tombstone 的 `BodyMetricDoc` 派生。
12. “我的”页入口拆分后，主题设置不再混在个人资料编辑中；首版应用设置只持久化 themeId 和 weightUnit。
13. 日期/时间段备注可新增、编辑、删除，并能在日历或趋势视图中以轻量标记或数量被看见；single_day、date_range、open_ended 三种范围类型语义清晰，禁止 `startDate > today`，生效查询按 `queryEnd <= today` 的闭区间重叠口径执行，同一天允许多条生效备注但不会自动合并。
14. 分享图本地生成，不上传服务端；首版只覆盖一个固定模板的训练详情分享图，输出 1080px 宽 PNG，高度随内容自适应；预览页提供保存图片和系统分享两个动作，不提供复制文字兜底；默认展示训练摘要和动作摘要，动作摘要行包含组数、最佳组和动作总容量；“显示明细”运行时选项可生成包含所有动作和所有训练组明细的长图，不设条数上限、不分页；若本次训练产生 PR/RM 刷新事件，默认显示“本次刷新 N 项记录”和最多 2-3 条动作指标摘要，不新增独立开关，也不展开 RM 公式明细；备注摘要只读取 `WorkoutDoc.note`，不自动带入 `TimelineNoteDoc`；短标签直接使用 `ExerciseDoc.category`；固定模板不显示昵称、头像、身高、体重、体脂或围度等个人资料和身体数据；使用当前主题 token，但不提供分享图主题选择或默认样式偏好；生成失败时 toast 提示并保留预览或重试入口，不创建业务记录。
15. P4.1 新增/重构页面满足主题语义迁移门禁，不新增散落硬编码颜色。
16. 未配置 WebDAV、无网络或同步失败时，新增功能仍能本地使用。
17. P5 AI 仍保持后置，文档和 UI 不宣称 AI 能力已实现。

代码实现交付时仍需遵守项目级验证命令；本需求文档本身属于纯文档任务，不触发 build/test/android sync。
