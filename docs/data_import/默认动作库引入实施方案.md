### 2.3 筛选与评分权威（v1）

后续所有默认动作扩展都使用本节评分，不在临时候选文件、历史对话或实现代码中另行定义一套口径。评分用于排序和暴露取舍，不代替证据核对、策展判断或硬性排除规则；A/B 等级和分数只保存在策展文档，不进入 `ExerciseDoc`、生成产物或运行时 UI。

每项使用 0–5 的整数分，顺序固定为：

```text
通用性 / 训练价值 / 可获得性 / 动作覆盖 / IronLog 可记录性 / 冗余惩罚 / 数据质量
```

总分公式固定为：

```text
总分 = 通用性 + 训练价值 + 可获得性 + 动作覆盖 + IronLog 可记录性 - 冗余惩罚 + 数据质量
```

理论范围为 -5 至 30。候选表必须写成 ``a/b/c/d/e/f/g=总分``，并附一条能够解释等级和主要取舍的理由；禁止只写总分或事后为等级反推分数。

| 指标 | 0 分锚点 | 3 分锚点 | 5 分锚点 |
|---|---|---|---|
| 通用性 | 仅适用于罕见专项、康复/医疗场景或极少数人群 | 常见于某一训练流派、进阶阶段或特定人群 | 力量、增肌、体能或居家计划中广泛可识别、可使用 |
| 训练价值 | 目的不清、动作语义矛盾或几乎没有独立训练价值 | 有清晰的辅助、孤立或技术训练目的 | 代表重要动作模式，或有明确且不可替代的基础训练目的 |
| 可获得性 | 依赖罕见、专用或难以确认的器械与场地 | 常见商业健身房可用，但居家受限，或反之 | 自重或杠铃、哑铃、绳索、常见固定器械等普遍可获得条件 |
| 动作覆盖 | 只重复目录中已经充分覆盖的模式 | 提供有意义的方向、单侧、张力曲线或训练目的差异 | 补足尚缺的水平推/拉、垂直推/拉、蹲、髋铰链、单腿、核心、手臂、小腿或心肺基础模式 |
| IronLog 可记录性 | 现有唯一 `type` 和组数据无法表达核心训练量，例如必须同时记录负重与距离 | 可选定唯一 `type`，但会丢失有价值的次要记录维度或需明确使用边界 | 能用唯一 `type` 和现有组字段清楚、稳定地记录，无需猜测或额外模式 |
| 冗余惩罚 | 动作语义和记录价值明显独立 | 与现有动作有较大重叠，但器械、方向、单侧性或训练目的仍形成有价值差异 | 主要只是握距、站姿、角度、版本号或器械上的低价值细分 |
| 数据质量 | 名称、步骤、肌群或器械严重矛盾，且无法根据固定证据可靠策展 | 原始字段存在重复、翻译或安全边界问题，但能逐项标注并形成可靠映射 | 中文步骤完整，名称、器械和肌群字段一致，几乎无需纠错 |

1、2、4 分按相邻锚点之间的接近程度取整；证据同时符合两个区间时采用较保守分值，并在候选理由或异常列写明决定因素。

`动作覆盖` 和 `冗余惩罚` 必须相对于策展当时的完整默认目录计算，因此目录变化后允许重评；当前目录只用于识别覆盖、重复、稳定 ID 和引用影响，不能反向充当上游候选集或正确答案。IronLog 自编动作的数据质量按中文名称、说明、安全边界和字段内部一致性评分，不因没有 upstream 自动扣分或加分。

等级采用建议区间而非机械阈值：

- A 级通常为 25–30 分，并且适合作为基础目录；若低于 25 分，必须明确说明其基础模式覆盖或普适价值为何足以进入 A。
- B 级通常为 20–24 分；总分达到 25 以上但受器械、技术、适用人群或目录冗余限制时仍列 B，并明确限制。
- 低于 20 分通常排除；确需保留时必须记录不可替代价值和人工批准依据。

无论总分多高，出现以下任一情况都不得直接入选：外部导入缺少固定原始记录或许可证证据；名称、步骤或字段矛盾且无法可靠纠正；现有记录类型无法表达动作的核心训练量；仅是低价值细分变体；康复、医疗或高风险动作缺少足够使用边界。没有合格上游记录但动作本身值得加入时，必须进入单独的 IronLog 自编候选节，明确无 upstream、无 provenance，不得借用相似记录。

每次改动评分口径都必须在本节提升版本并说明受影响指标；只重评受规则变化或目录覆盖变化影响的候选，不为追求分数分布机械改写已经有充分证据的判断。

## 3. 目标领域契约

P1 第 2.3 节是 `ExerciseDoc` 唯一领域权威。实施目标如下；P2 只记录持久化链路状态。

```ts
type ExerciseCategory =
  | "chest" | "back" | "legs" | "shoulders" | "arms"
  | "core" | "cardio" | "stretch" | "other";

type EquipmentId =
  | "body_weight" | "barbell" | "dumbbell" | "cable" | "machine"
  | "band" | "kettlebell" | "ab_wheel" | "stationary_bike"
  | "jump_rope" | "elliptical" | "stepmill" | "trap_bar"
  | "external_weight" | "other";

interface ExerciseProvenance {
  source: string;
  sourceId: string;
  sourceRevision: string;
}

interface ExerciseDoc extends BaseDoc {
  name: string;
  category: ExerciseCategory;
  type: ExerciseType;
  equipment: EquipmentId | null;
  description: string | null;
  primaryMuscleGroupIds: MuscleGroupId[];
  secondaryMuscleGroupIds: MuscleGroupId[];
  provenance?: ExerciseProvenance;
  isCustom: boolean;
  replacedByExerciseId: string | null;
}
```

运行时约束：

- 有上游来源的内置动作 `provenance` 固定为 `{ source: "hasaneyldrm/exercises-dataset", sourceId: <四位上游 ID>, sourceRevision: <固定 SHA> }`；IronLog 自编内置动作省略该可选字段，不得伪造来源。
- 自定义动作没有 provenance；create/update payload 不接受该字段。core/persistence 的 `ExerciseDoc` 可以保存 provenance，但页面使用的 `Exercise`、`ExerciseDetail` 和列表/搜索/筛选 DTO 必须由显式白名单 mapper 构造，运行时对象也不得含有该 key，而不只是“不渲染”。repository 更新必须从已存 `ExerciseDoc` 合并受控 patch，不能由页面 DTO 重建整条文档而丢失 provenance。
- `equipment` 是产品字段：内置动作由映射生成，自定义动作可在共享表单单选，列表、详情和选择器可显示与筛选。
- `description` 是一个字符串。`candidates.md` 正文中的 `↵`/`↵↵` 转成 `\n`/`\n\n`；状态文字不进入字段。trim 后为 1–500 字符或 `null`，内部换行不压平。候选允许单段压缩说明；默认跑步条目实际包含 `↵` 以验收内置说明分段，`↵↵` 由专用 fixture 验证，不得从上游步骤自动拼接。
- `category` 不含 `compound`。本轮不增加 `movementPattern`。
- `primaryMuscleGroupIds` 最多 3 个，`secondaryMuscleGroupIds` 最多 6 个；组内唯一、主次不交叉、枚举合法。
- [首批已完成的 schema 边界] 首批实施前从 schema 2 直接升级到 3，只支持“存储不存在”的首次初始化；任何非 3 旧开发快照均明确拒绝，不迁移、不静默丢弃，也不由应用自动清除。
- [扩展批次前置条件] 开始扩展实施时必须断言 `CURRENT_SCHEMA_VERSION === 3`。本批保持 3，不修改版本号、不增加 migration。若实施时版本已不再是 3，停止并按当时字段形状重新评估，不得机械套用本方案。
- [扩展批次契约变化] 当前代码的 `EquipmentId` 尚无 `trap_bar`。实施六角杠硬拉前，必须先在 P1 字段契约矩阵登记该受控枚举扩展，再同步 core 枚举、中文标签、生成映射、service 校验和测试；它不新增 `ExerciseDoc` 属性。

自定义动作写入契约必须明确区分 `undefined` 与 `null`：

```ts
interface CreateExerciseInput {
  name: string;
  category: ExerciseCategory;
  type: ExerciseType;
  equipment: EquipmentId | null;
  description: string | null;
  primaryMuscleGroupIds: MuscleGroupId[];
  secondaryMuscleGroupIds: MuscleGroupId[];
}

interface UpdateExerciseInput {
  name?: string;
  category?: ExerciseCategory;
  type?: ExerciseType;
  equipment?: EquipmentId | null;
  description?: string | null;
  primaryMuscleGroupIds?: MuscleGroupId[];
  secondaryMuscleGroupIds?: MuscleGroupId[];
}
```

create 必须显式提供唯一 `type`，不得因遗漏暗中回退为 `strength`；未设置 equipment/description 时页面提交 `null`。update 中 `undefined` 表示不修改，`null` 只用于显式清空 equipment/description。两种输入都不包含 provenance、ID 或 BaseDoc 元字段。

### 4.4 type

| type | 唯一记录语义 | 策展边界 |
|---|---|---|
| `strength` | 外部负重 + 次数 | 可用 kg/lb 表达的自由重量、绳索和固定器械 |
| `reps_only` | 仅次数 | 动态自重、辅助引体和不记录弹力带张力的动作 |
| `static_hold` | 保持时间 | 侧平板等静态保持 |
| `cardio` | 距离和/或持续时间 | 跑步和心肺器械 |

候选表 type 是最终权威。上游 `cardio` 只表示动作分类，不直接决定产品记录类型；跳绳、波比、登山跑和弹力带帕洛夫固定 `reps_only`。跑步、固定自行车、椭圆机和踏步机固定 `cardio`。未来若需要另一记录语义，新增独立动作 ID，不修改本模型。

```text

```

`exerciseCatalog.mjs` 使用 Node 内置模块，不新增运行时依赖，提供：

- `npm run catalog:generate`：读取 `docs/data_import/candidates.md`，从固定 commit 的上游 JSON 在内存中核对记录，生成纯 TypeScript 数组。
- `npm run catalog:check`：不联网，重新解析 `docs/data_import/candidates.md` 并核对已提交产物中的候选哈希、数量、稳定 ID、上游 ID 和字段约束；build/test 前运行。

生成文件头必须包含候选文件哈希、上游 commit 和“禁止手改”提示，不写每次运行都会变化的生成时间，保证同一输入得到相同产物。生成文件输出 `DefaultExerciseSeed[]`，只包含 `id`、名称、category、type、equipment、description、主次肌群和可选 provenance；不得伪装成已经具备 BaseDoc 元字段的 `ExerciseDoc[]`，也不得包含评分、A/B 等级、上游英文说明、其他语言、媒体或完整原始记录。

`defaultData.ts` 使用现有固定 `seedTime = "2026-01-01T00:00:00.000Z"` 将每条 seed 唯一地补成 `ExerciseDoc`：`createdAt=updatedAt=seedTime`、`deletedAt=null`、`schemaVersion=CURRENT_SCHEMA_VERSION`、`isCustom=false`、`replacedByExerciseId=null`。禁止调用当前时间生成默认元字段；同一候选文件和代码版本必须得到字节级稳定的默认目录。
