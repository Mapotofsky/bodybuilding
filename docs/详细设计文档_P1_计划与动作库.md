# P1 详细设计文档：计划、模板、动作库与日历

> 对应概要设计：M2 计划、模板与动作库
> 状态：计划/模板/动作库列表、Tab、63 条精选默认动作、受控记录方式、重量口径与计数口径均为当前实现基线
> 前置依赖：P0 核心训练、P2 本地文档存储与迁移。

---

## 1. 模块职责与范围

本模块让单人用户以计划和模板组织训练，并把模板关联到本地训练记录和日历。模板是动作过滤器与文字提示，不是预设重量/次数/组数的处方系统。

包含：计划 CRUD、模板 CRUD、模板动作编排、动作详情、动作库列表与底部 Tab、weekly/cyclic/flexible 日历、首页今日计划和按模板训练入口。当前动作详情入口是动作库列表；训练详情和动作历史会解析并展示历史动作引用，但不提供从训练记录跳转到动作详情的入口。

不包含：多人共享计划、云端计划库、模板拖拽排序、自动填充训练组、服务端排程任务、复杂完成率或连续打卡指标，以及 AI 自动写入计划或训练。

动作详情的信息架构参考 [workout-cool 的动作属性与统计界面](https://github.com/Snouzy/workout-cool/tree/77f25a922b51be7d96bd051c5d2096959f0d61a8)：将主/次目标肌群、动作说明和个人表现置于同一详情上下文。该仓库采用 Prisma、账户、服务端 API、外链视频和会员能力，均不是 IronLog 依赖；其动作文本、媒体和统计实现也不直接复用。IronLog 只采用离线信息层级，数据链路仍服从 P0/P2/P3。

## 2. 持久化模型

### 2.1 TrainingPlanDoc

```ts
interface TrainingPlanDoc extends BaseDoc {
  name: string;
  description: string | null;
  color: string;
  mode: "weekly" | "cyclic" | "flexible";
  cycleLength: number | null;
  isActive: boolean;
}
```

### 2.2 TemplateDoc

```ts
interface TemplateDoc extends BaseDoc {
  planId: string;
  name: string;
  sortOrder: number;
  color: string | null;
  scheduleRule: Record<string, unknown> | null;
  exercises: Array<{
    id: string;
    exerciseId: string;
    sortOrder: number;
    note: string | null;
  }>;
}
```

`scheduleRule` 约定：

```json
{ "day_of_week": [1, 3, 5] }
{ "day_in_cycle": 2 }
null
```

周一为 1，周日为 7。cyclic 的 `day_in_cycle` 必须为整数且位于 `1..cycleLength`；校验在 `services/plan.ts` 的 `validateTemplateScheduleRule` 完成。

`TemplateExerciseDoc.id` 是稳定嵌套 ID。读取模板进入 TemplateEditPage 时必须保留既有 ID；保存模板时未变更的动作条目不得无故重建 ID；只有新增模板动作可以缺省 ID 并由 repository 分配。该 ID 随 `templates.json` 往返，用于减少 WebDAV 合并噪音并支撑后续嵌套字段演进。

### 2.3 ExerciseDoc 与历史引用

动作使用 string ID。内置动作 `isCustom=false`，只能由默认数据契约修正，页面和 service 不允许编辑或删除；用户创建的动作 `isCustom=true`，ID 采用 `custom-ex-<generated-id>` 命名空间（通常为 UUID，运行环境不提供 `crypto.randomUUID()` 时使用回退 ID），编辑时 ID 不变。

以下是当前 `ExerciseDoc` 领域权威契约，六项记录配置、`equipment`、`provenance` 和受限 `ExerciseCategory` 已随 63 条精选目录接入完整数据链路。

```ts
type ExerciseCategory =
  | "chest" | "back" | "legs" | "shoulders" | "arms"
  | "core" | "cardio" | "stretch" | "other";

type EquipmentId =
  | "body_weight" | "barbell" | "dumbbell" | "cable" | "machine"
  | "band" | "kettlebell" | "ab_wheel" | "stationary_bike"
  | "jump_rope" | "elliptical" | "stepmill" | "external_weight" | "other";

type MuscleGroupId =
  | "chest" | "back" | "shoulders" | "biceps" | "triceps" | "forearms"
  | "core" | "glutes" | "quadriceps" | "hamstrings" | "calves"
  | "adductors" | "abductors" | "full_body" | "other";

type RecordingMode =
  | "weight_reps" | "reps" | "reps_duration" | "duration" | "distance_duration"
  | "weight_duration" | "weight_distance_duration";

type LoadBasis = "total" | "per_hand";
type CountBasis = "whole_set" | "per_side";
type LoadDirection = "higher_better" | "lower_better";
type RateMetric = "none" | "reps_per_time" | "distance_per_time" | "load_distance_per_time";
type ContextKind = "none" | "resistance_level" | "incline_percent";

interface ExerciseProvenance {
  source: string;
  sourceId: string;
  sourceRevision: string;
}

interface ExerciseDoc extends BaseDoc {
  name: string;
  category: ExerciseCategory;
  recordingMode: RecordingMode;
  loadBasis: LoadBasis | null;
  countBasis: CountBasis;
  loadDirection: LoadDirection | null;
  rateMetric: RateMetric;
  contextKind: ContextKind;
  equipment: EquipmentId | null;
  description: string | null;
  primaryMuscleGroupIds: MuscleGroupId[];
  secondaryMuscleGroupIds: MuscleGroupId[];
  provenance?: ExerciseProvenance;
  isCustom: boolean;
  replacedByExerciseId: string | null;
}
```

字段语义：

- `category` 是面向用户的 IronLog 导航分类，不照抄上游 `category/body_part`。`compound` 不是身体部位分类，导入后从受控集合删除；深蹲、硬拉等归入 `legs`。动作模式将来可由独立 `movementPattern` 字段表达，本轮不预建空字段。
- 每条动作恰好有一个 `recordingMode`，不增加多模式集合，模板和训练中也不能切换。`reps_duration` 复用 `reps` 和 `durationSec`，用于时间必填、次数可选的爬楼机；频率只在两者同时存在时派生。
- `contextKind` 只能是 `none`、`resistance_level` 或 `incline_percent`，以单选结构排除同一动作同时记录阻力和坡度。阻力动作只保存训练事实且强制 `rateMetric=none`；当前内置阻力动作仅为椭圆机和固定自行车，档位允许 `[0,200]` 的小数。坡度不得为负，因此不支持跑步机下坡。
- 不含重量的模式要求 `loadBasis=null`、`loadDirection=null`；含重量的模式两者必填。每个动作始终必须有 `countBasis`。`distance_per_time` 只允许同时包含距离和时间的模式，`load_distance_per_time` 只允许 `weight_distance_duration`，其余默认 `none`。非法组合不能进入 service、repository 或生成目录。
- `total` 表示输入值就是该动作单次实际使用的负重；`per_hand` 只表示输入的是每手重量，默认用于双手等重动作。`whole_set` 表示次数、距离和时间描述整组；`per_side` 表示一次输入的是每侧值，聚合训练量按左右两侧合计。两种口径互不推导：不得从器械、动作名称或 `per_hand` 推断 `countBasis`。同为哑铃，双哑铃卧推可为每手重量且整组填写，高脚杯深蹲仍为总重量。当前没有左右侧字段，不记录左右重量、次数、距离、时长、PR 或休息时间差异。
- 自定义动作在尚未被训练引用前可以调整六项记录配置；一旦任一未删除训练已经保存该动作的 `WorkoutExerciseDoc` 快照，repository 必须拒绝再修改 `recordingMode`、`loadBasis`、`countBasis`、`loadDirection`、`rateMetric` 或 `contextKind`。名称、说明、器械和肌群等非记录约定字段仍可编辑，避免把同一动作的历史成绩混入不同口径。
- `higher_better` 表示普通负重；`lower_better` 表示辅助重量，比较时更小可更优。`added` 和 `generic` 不持久化为独立概念。
- 前端重量标签只由口径和方向派生：普通总负重显示“重量”，普通每手口径显示“每手重量”，`lower_better` 显示“辅助重量”。计数口径显示“整组填写”或“每侧填写”；每侧动作的次数、距离和时间输入标签明确标明“每侧”，但不拆成左右两行。
- `equipment` 是 IronLog 规范化器械字段，与来源信息无关。内置动作由策展映射，自定义动作由共享表单编辑；未知或确实不适用时为 `null`。
- `description` 是唯一动作说明字段，保存不含 HTML 的中文纯文本。允许使用 `\n` 和 `\n\n` 表达步骤与段落，详情页必须保留这些换行；不新增 `instructionStepsZh`、`techniqueSteps` 或其他并列说明字段。提交时 trim 后总长度仍不得超过 500 个字符。
- `target` 与 `muscle_group` 经策展融合进 `primaryMuscleGroupIds`；`secondary_muscles` 映射、去重后进入 `secondaryMuscleGroupIds`。主肌群最多 3 个、次肌群最多 6 个，组内唯一、主次不交叉且只能使用现有 `MuscleGroupId`。
- `provenance` 是可选、只读的目录维护信息，集中容纳 `source/sourceId/sourceRevision`。它只由默认目录生成链写入。core/persistence 的 `ExerciseDoc` 保留该对象；页面 `Exercise`、`ExerciseDetail`、列表和搜索结果必须经显式白名单 mapper 构造，运行时对象不得含该 key，自定义表单与 service payload 也不接受它。repository 更新必须从已存文档合并受控 patch，不能由页面 DTO 重建文档。上游原始分类、肌群和说明不复制进运行时文档；provenance 表示策展来源，不表示中文名称或说明是上游语义的忠实转写。

自定义动作删除采用 tombstone。若选择替代动作，删除记录写入 `replacedByExerciseId`，并在同一次 repository mutate 中把存活模板里的 `exerciseId` 改为目标 ID；替代目标必须与源动作的 `recordingMode`、`loadBasis`、`countBasis`、`loadDirection`、`rateMetric` 全部相同，避免合并不可比较的历史。WorkoutDoc 内的历史 `exerciseId` 不批量改写。读取侧沿有向链解析当前名称与分类，必须防自环、循环和最大深度；无目标或无替代时显示 `动作#原ID`。`WorkoutExerciseDoc` 的五项训练快照始终优先于替代动作当前配置。

`0.1.0-internal.2` 已成为兼容基线。当前 schema、支持版本、稳定 ID 目录融合和数据保留规则由 P2 完整定义；P1 只要求动作字段与引用在迁移后仍满足本节领域契约，不复制迁移矩阵。

## 3. Service 调用契约

文件：`frontend/src/services/plan.ts` 与 `frontend/src/services/exercise.ts`。

| 函数 | 行为 |
|---|---|
| `getPlans()` / `getPlan(id)` | 从 LocalJsonRepository 读取有效计划，映射成页面兼容类型。 |
| `createPlan` / `updatePlan` / `deletePlan` | 操作 TrainingPlanDoc；默认颜色为 `#10B981`。 |
| `addTemplate` / `updateTemplate` / `deleteTemplate` | 操作 TemplateDoc；exercises 更新是全量替换，缺少 ID 时 repository 分配 ID。 |
| `getTemplate(id)` | 返回模板与动作详情，供 WorkoutCreatePage 激活过滤。 |
| `appendExerciseToTemplate(templateId, exerciseId)` | active template 下新建动作后追加到当前模板；已存在时幂等返回；不得要求页面拼完整模板。 |
| `getCalendar(from, to)` | 组合自动排程和本地 WorkoutDoc 完成状态。 |
| `getExerciseDetail(id)` | 读取本地动作、器械、分段 description、历史组记录所需信息，并调用 P0 的派生个人统计；不写入统计快照，也不把 provenance 返回给页面。 |
| `createExercise` / `updateExercise` / `deleteExercise` | 仅操作自定义动作；校验名称、受控分类、完整记录配置、equipment、description 和目标肌群字段；不接收 provenance；create 必须显式接收完整合法组合、`equipment: EquipmentId \| null` 和 `description: string \| null`；update 的可清空字段使用 `undefined=不修改、null=显式清空`；删除可选择 null 或记录配置完全兼容的有效替代动作。 |

页面类型保持 `plan_id`、`schedule_rule`、`exercise_id` 等 snake_case；持久化模型保持 camelCase。新增字段必须同时维护 service 输入、mapper、core 文档和读取端。

## 4. 日历生成规则

### 4.1 数据来源与合并顺序

`getCalendar(from, to)` 读取有效计划、模板和范围内训练，按以下顺序构造：

1. 对每个启用计划生成 weekly 或 cyclic 虚拟条目。
2. 以 `(templateId, date)` 查询本地 WorkoutDoc 的 `planTemplateId`，标记已完成并写入 `workoutId`。
3. 注入范围内、已经关联模板但未由虚拟条目覆盖的实际训练，避免历史完成训练消失。
4. 生成 `from..to` 每一天的 `CalendarDay`，即使 entries 为空。

当前只有 HomePage 消费 `getCalendar` 展示当天计划和补训建议。CalendarPage 仍只调用 P0 `getWorkouts` 渲染实际训练记录；不得把 HomePage 的计划条目能力写成 CalendarPage 已实现能力。

### 4.2 weekly

- 从 `max(from, plan.createdAt 的日期部分)` 开始遍历。
- 当前日期的星期值在 `scheduleRule.day_of_week` 中时生成条目。
- 没有规则的模板不自动生成。

### 4.3 flexible

不自动生成日历条目或首页待训练提醒。用户仍可在 WorkoutCreatePage 内手动选择该计划的模板开始训练。

### 4.4 cyclic：当前实现与限制

当前 `cyclicEntries`：

1. 按 `TemplateDoc.sortOrder` 排序模板。
2. 从 `max(from, plan.createdAt 日期, today)` 开始。
3. 从排序后的第一个模板开始，根据相邻 `day_in_cycle` 的间隔推进。
4. 范围内已完成训练由第 4.1 节的实际训练注入逻辑保留。

当前实现**不会**根据“最近一次完成训练”决定下一模板。它是基础排程，适合展示预期序列，但不等价于严格的完成驱动循环。未来改进必须把调度计算迁入 `core`，并至少测试：正常路径、今日完成、范围内/范围外完成、无历史记录四种边界。

### 4.5 日历与月统计

CalendarPage 为补齐月历网格会查询 `calStart..calEnd` 范围内的实际训练记录；该范围可以包含相邻月。月训练次数必须额外按 `monthStart..monthEnd` 过滤，不能把网格溢出日期计入标签为“本月”的统计。当前 CalendarPage 不渲染计划条目，也不提供未完成计划条目跳转。

## 5. 按模板训练

### 5.1 两条入口

| 入口 | 触发 | 必须行为 |
|---|---|---|
| URL 入口 | 首页今日计划/补训建议跳转 `/workouts/new?template_id=X` | 加载对应模板并激活动作过滤。 |
| 页内入口 | 首页/列表的普通开始训练进入 `/workouts/new` 后选择计划和模板 | 选择后得到与 URL 入口完全相同的过滤和备注行为。 |

### 5.2 过滤契约

```ts
const filteredExercises = allExercises.filter(
  (exercise) => !activeTemplate || templateExerciseIds.has(exercise.id)
);
```

这是“仅显示”的实现：非模板动作不渲染。不得替换为排序、置顶、高亮或分组。训练保存时必须传 `plan_template_id`，以便详情 badge、日历完成状态和复制训练保持关联。

`WorkoutExerciseDoc.supersetGroup` 属于 P0 训练聚合文档的预留字段，不是 P1 模板动作编排能力。当前 UI 不提供 superset 编排；训练编辑页保存模板关联或动作列表时不得清空已有 `supersetGroup/superset_group`。

### 5.3 模板备注

模板动作 `note` 在训练中的作用是文字提示，默认占位使用“填写训练提示”，不得假定所有动作都按次数记录。它不能自动生成组数、重量、距离、时间、RPE 或 restSeconds；这些仍由实际 WorkoutDoc 记录。

### 5.4 统一动作选择器与自定义动作入口

`ExercisePicker` 是训练新建、训练编辑和模板编辑共享的选择器。三个入口均提供搜索、分类筛选、器械筛选和“新建自定义动作”。创建和编辑自定义动作必须复用共享 `CustomExerciseForm`，字段为：名称、分类、记录方式、器械、重量口径、计数口径、成绩方向、受控竞速指标、适用上下文、分段说明和主次肌群。界面使用“负重 + 次数、仅次数、次数 + 时间、保持时间、距离 / 时间、负重 + 时间、负重 + 距离 / 时间”等用户文案，不暴露内部字段名。不含重量的模式隐藏重量口径与成绩方向；上下文只在适用动作显示。表单状态只能构成合法组合。快速创建与完整编辑必须通过同一状态和 service 输入提交；create 显式提交完整记录配置，未设置 equipment/description 时提交 `null`；update 未编辑字段传 `undefined`，用户清空可清空字段时传 `null`。`provenance` 不进入表单或页面输入。创建成功后：新建训练页选中该动作、训练编辑页追加带默认组的动作、模板编辑页追加模板动作。页面只调用 `services/exercise.ts`，不直接访问 repository。

sheet 形态的 `ExercisePicker` 必须高于固定底部导航，列表使用动态视口高度、独立纵向滚动和底部 safe area；模板、训练编辑两个 sheet 入口共享同一层级规则。模板颜色必须选择一个实际颜色；新建模板默认继承计划颜色，编辑页不提供“无”选项。

active template 下通过 `ExercisePicker` 新建动作时，新动作必须追加到当前模板，然后刷新 `activeTemplate`、计划模板缓存和动作列表，保证“仅显示模板动作”的过滤仍成立。该规则同时覆盖 URL 模板入口和页内模板选择入口，也覆盖完成至少一组后点击“换动作”返回选择页再新建动作的路径。`ExercisePicker` 的 `onCreated` 与 `onSelect` 不能导致新建动作被二次 toggle 取消选中。

### 5.5 字段契约矩阵

| 字段/行为 | 页面展示 | 页面编辑 | service 输入 | mapper/repository/migration | WebDAV 往返 | 状态 |
|---|---|---|---|---|---|---|
| `TemplateExerciseDoc.id` | 不直接展示 | TemplateEditPage 读取并随保存传回；新增动作可为空 | `TemplateExerciseCreate.id?` | `toTemplate` 保留；repository 缺失时补 ID | `templates.json` | 已实现 |
| active template 新建动作追加 | 当前选择页立即可选 | 新建动作后追加当前模板 | `appendExerciseToTemplate(templateId, exerciseId)` | 使用现有模板动作并只追加新增条目 | `templates.json` | 已实现 |

### 6.1 动作库列表页面契约

路由为 /exercises。底部导航固定为：首页、动作库、计划、日历、我的；动作库位于首页和计划之间。活动状态按当前 pathname 是否以 /exercises 开头判断。P4 负责五项导航的视觉 token、触控尺寸和移动端视觉验收；本节只定义信息与交互。

列表首次进入调用 getExercises()；默认顺序沿用现有 service 的分类、名称排序。搜索输入传 q，分类筛选传 category，器械筛选传 equipment，三者可组合；筛选状态保留在 URL query 中，刷新、从详情返回和底部 Tab 重入时保持。分类来自受控集合且不含 `compound`。列表卡片展示名称、分类、记录方式、器械和“自定义”标识；不显示动作图标；内置动作不显示“内置”标签，不展示来源信息，也不展示或持久化派生统计。

列表提供“新建自定义动作”入口，复用现有名称、分类、记录方式和说明的 service 校验。创建成功后返回当前筛选下的列表并显示新记录。列表点击进入 /exercises/:id；编辑只在详情页提供，删除可在详情页或自定义动作卡片左滑后发起，内置动作不显示这些操作。列表进入详情时传回跳 URL；详情页返回优先使用该 URL，直接访问或缺少来源时回到 /exercises。

页面必须具备加载、空库、无搜索结果和读取失败状态。删除确认使用全局 ConfirmDialog；删除成功后回到保留筛选的动作库列表。替代删除、模板原子更新和历史快照规则仍以第 2.3 节为准。

自定义动作卡片支持左滑露出“删除”操作；内置动作不响应删除左滑。左滑只揭示操作，不得直接 tombstone：点击后进入与详情页相同的替代动作选择和 ConfirmDialog，确认后调用 `deleteExercise`。垂直滚动不能误触发左滑；同一时刻最多展开一张卡片，右滑、点击其他卡片或滚动后收起。左滑不是唯一删除入口，详情页的可访问删除操作必须保留；删除成功后移除当前卡片并保留原筛选状态。

### 6.2 完整动作详情

详情页保持现有路由 `/exercises/:id`，信息顺序固定为：

1. 名称、分类、记录方式、重量口径、成绩摘要、器械与自定义标识；不显示动作图标；内置动作不显示“内置”标签或 provenance；
2. “目标肌群”：主目标肌群在前、次要目标肌群在后，以本节 `MuscleGroupId` 映射本地标签；
3. `description` 作为“动作要领”按纯文本原有换行展示段落与步骤；
4. “我的统计”：只呈现 P0 返回的已完成训练聚合；
5. 现有历史组记录与仅自定义动作可用的编辑/删除操作。

目标肌群和 description 缺失时显示“暂无”，不能从分类、历史重量或模型输出推断。首期不嵌入外链视频、GIF、远端图片、HTML 富文本、1RM 估算、趋势图或医学/个体化训练结论；这些均不应以“动作详情已实现”对外宣称。

自定义动作编辑表单包含：受控分类、唯一记录方式、计数口径、仅在含重量模式显示的重量口径和成绩方向、兼容的竞速指标、规范化器械、主目标肌群 0 至 3 个、次要目标肌群 0 至 6 个，组内不可重复且两组不得交叉；`description` 是唯一的动作要领输入，沿用现有 trim 后最多 500 个字符的纯文本约束，并保留内部换行。内置动作不显示编辑入口；内置说明和 provenance 只通过默认目录生成链更新，不能在页面改写。兼容基线后的字段和目录演进必须遵守 P2 migration；本节不授权重置 IndexedDB、Android 应用数据或 WebDAV 快照。动作说明是一般训练提示，不是医疗诊断或自动处方。

个人统计由 P0/P7 计算，页面不得重新遍历 WorkoutDoc 或自行累计。P1 只展示与历史快照匹配的成绩：负重次数、辅助重量、距离/时间、负重时间和负重距离分别使用注册指标，并保留原始重量、次数、距离、时间及重量/计数口径上下文。重量 PR 和估算 1RM 使用输入重量换算后的值；聚合训练负载使用 core 的双倍率语义。空历史显示暂无，读取失败显示错误状态；统计不会因未配置 WebDAV、无网络或缺少 AI 而不可用。

当前调用链：

```text
ExerciseLibraryPage -> getExercises() -> ExerciseDetailPage
ExerciseDetailPage -> getExerciseDetail() / getExerciseHistory()
                   -> P0 个人统计聚合
                   -> LocalJsonRepository -> DocumentStore
自定义动作编辑 -> updateExercise() -> LocalJsonRepository
```

### 6.3 与 P5 的依赖摘要

P5 的计划候选导入在动作引用上调用本模块规则：已有动作按现有重定向链解析；未知动作必须由用户映射、创建候选自定义动作或拒绝导入。候选 JSON、预览和批量导入流程由 P5 定义。

## 7. 验收与回归场景

| 场景 | 期望 |
|---|---|
| 创建 weekly 计划 | 指定星期的范围内日期生成对应模板。 |
| 创建 flexible 计划 | 无自动条目或首页待训练提醒，仍可在训练页选择模板。 |
| 创建 cyclic 计划 | 周期日校验拒绝 0、非整数和大于 cycleLength 的值。 |
| 模板 URL 入口 | 非模板动作完全不渲染，保存后 workout 关联模板。 |
| 模板页内入口 | 与 URL 入口行为一致。 |
| 模板训练复制 | 新训练保留 `planTemplateId` 与组 restSeconds。 |
| 自定义动作创建 | 三个动作选择入口均可创建；ID 为 `custom-ex-` 命名空间，并进入当前训练或模板上下文。 |
| 自定义动作迁移删除 | 原动作 tombstone；仅允许记录配置完全一致的替代目标；活跃模板替换，历史快照和历史 ID 保留。 |
| 月历统计 | 相邻月网格数据不污染本月训练次数。 |
| 动作库默认状态 | 按分类、名称展示有效内置和自定义动作；列表显示名称、分类、类型和自定义标识。 |
| 动作库筛选与导航 | 搜索与分类可组合并保留在 URL；五项导航中动作库活动状态正确；详情返回保留筛选。 |
| 动作库异常与变更 | 加载、空库、无结果、读取失败状态可见；新建后回到当前列表；详情或自定义动作左滑删除均经替代选择和 ConfirmDialog，成功后保留筛选并满足替代/历史回归。 |
| 完整动作详情 | 器械、主/次目标肌群和分段 description 按第 6.2 节显示；内部换行可见，缺失数据明确显示暂无，不从分类推断，不展示 provenance，也不加载外链媒体。 |
| 动作目录契约 | 每条动作只有一个记录方式和合法五项组合；分类无 `compound`；主次肌群合法且不重复；description 不超过 500 字。 |
| 个人统计 | 仅使用 P0/P7 返回的本地已完成训练聚合；热身、替代解析、用户当前单位换算和历史记录快照的口径不在页面重复实现。 |
| 左滑删除 | 仅自定义动作可左滑露出删除；纵向滚动不误触发，点击删除后仍需同类型替代选择与 ConfirmDialog，内置动作不可删除。 |
| 动作库窄屏 | 360px、412px 下五项导航和列表卡片无溢出、无裁切，触控区域可用。 |

提交前执行 `npm run build`、`npm test`、`npm run android:sync`。修改日历/过滤核心逻辑时，必须额外列出并走查边界场景。
