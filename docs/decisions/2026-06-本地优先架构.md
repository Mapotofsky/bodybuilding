# 决策记录：单人应用采用本地优先架构

> 背景材料日期：2026-06-22。本记录提炼当时仍有效的选型理由；不记录当前依赖版本、schema、实现进度或发布状态。

## 背景

IronLog 曾考虑前后端分离的多用户 Web 应用。面向单人训练日志的当前产品目标，需要离线记录、易于备份和较低运维成本；账号、数据库和业务服务器会增加部署与维护负担。Android 是主要使用平台，同时需要在浏览器中开发和验证。

## 决定与理由

- 以 React 应用复用页面和业务代码，以 Capacitor 提供 Android 容器及必要的原生能力。浏览器开发使用 IndexedDB，Android 使用应用私有文件存储；具体适配以[产品与架构](../reference/产品与架构.md)和[Android 平台与凭据](../reference/Android平台与凭据.md)为准。
- 业务数据采用可独立读写的 JSON 文档分片，训练按月拆分。单一大 JSON 文件虽简单，但每次训练都重写整体数据，扩大损坏和多设备冲突的影响范围。现行 schema 与兼容规则只在[本地存储与迁移](../reference/本地存储与迁移.md)定义。
- WebDAV 只承担用户自有空间中的手动同步与备份。它没有业务查询、事务或冲突合并能力，交互查询从本地快照完成；现行同步语义见[WebDAV 同步](../reference/WebDAV同步.md)。
- 页面经 service、repository 与 DocumentStore 访问数据，core 保持纯 TypeScript。直接在页面调用 Capacitor 或 WebDAV 会耦合浏览器、Android 和未来平台的实现；现行层次边界见[产品与架构](../reference/产品与架构.md)。

## 曾比较的路线

FastAPI 与 PostgreSQL 适合多用户、中心化权限和 SQL 查询，却要求维护服务、数据库、迁移、部署与备份，不适合作为当前单人版的运行路径。将 WebDAV 当数据库或让页面直接访问平台 API 同样不能满足离线本地真源与可替换适配器的目标。

## 后果与重新评估条件

本地真源免去业务服务器，并让离线功能独立于 WebDAV；代价是要显式处理 JSON 兼容迁移、备份恢复与多设备冲突。现有 LWW 同步的限制由[WebDAV 同步](../reference/WebDAV同步.md)说明。未来如明确引入多人协作、中心化权限或新平台，应先重新确定数据所有权、离线能力与冲突策略，再评估新的 repository 或平台适配器；本记录不预先批准 CloudBase、MongoDB 或其他具体服务。
