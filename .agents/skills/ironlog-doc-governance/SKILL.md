# IronLog 文档治理

## 权威职责

先读取 [概要设计文档](../../../docs/概要设计文档.md) 的文档职责表，再只读取本次概念的权威文档和受影响引用文档。概要设计定义产品范围、模块边界、跨模块不变量和文档权威归属；Px 细化各功能域。README、[运行指南](../../../docs/如何运行IronLog.md)、[部署指南](../../../docs/部署指南.md) 和技术路线只保留各自读者完成任务所需的信息。

## 内容去向

在会话内判断每项改动属于当前事实或限制、未来规划、方法或规则，据此选择事实源和权威位置。分类只服务于执行判断，不是交付文档的模板。最终正文直接呈现该文档读者需要的当前正向状态，不写入分类标签、任务提示、Skill、核验过程或治理过程。

当前事实和限制以与本次改动直接相关的代码、配置、脚本、版本元数据或 migration 为准；规划清楚表达未实现状态；完整方法或规则只保留在负责回答该问题的一个权威文档。非权威文档只保留其读者完成任务所需的摘要和链接。

历史信息只有在会改变当前行为、兼容、迁移、安全、发布、审计或故障诊断决策时才进入现行文档。数据兼容基线放在 P2，影响覆盖升级的版本信息放在相关操作说明；仍有当前价值的版本特定发布或设备验收集中在部署或发布职责下。过去尝试、旧验收叙事、纠错过程和防错声明若已不改变当前决定，直接删除并由 Git 历史保留，无需另找文档接收；必要的“当前版本尚未验证”边界只在负责当前发布状态的位置说明一次。

## 修改工作流

1. 在会话内确定每项事实、规则和状态的唯一权威位置，不创建治理台账。
2. 修改概要设计时检查下游 Px 是否仍在其边界内；修改详细设计时检查是否与概要设计冲突或越权定义其他领域。
3. 同一概念需要修改多份文档时，逐份确认独立读者职责；搜索只用于定位直接矛盾、重复权威和受影响引用，每个命中按所在文档的读者职责处理。
4. 文档职责变化、合并、拆分或归档时，搜索旧职责下的相关段落和链接，处理整个职责而不是只改标题或状态。
5. 删除或迁移仍影响当前决定的内容时，以当前行为证据、接收位置、仍有效的更一般规则或明确废止依据支撑改动；无法可靠判断时保留该项并报告。只承载已失去当前价值的历史叙事可以直接删除。
6. 保留文档履行权威职责所需的指标、算法、决策依据和验收方法；正交化只改变位置与引用，不自行改变产品或工程语义。

## 验收

- 只核对本次新增、删除、改写或作为判断依据的事实，并按事实类型选择直接证据；不把每次修改扩展为代码路径、命令、版本、schema、applicationId、路由和状态的全量盘点。
- 逐份抽查修改后的中文、标题层级、相对链接和读者语境；审查搜索命中的直接矛盾、重复权威和受影响引用。
- 执行 Skill 或仓库已有的结构检查、审查完整 diff 并运行 `git diff --check`；纯文档变化不运行产品构建、Android sync、Gradle 或设备测试。
- 成品描述当前产品、架构、操作方法或该文档职责内的明确规划，读者无需理解返工、核验或治理过程。

## 停止条件

- 影响当前决定的事实找不到可靠依据时，保留该项并报告未决点。
- 事实正确、职责清楚且读者可用后停止；相邻代码偏差单独报告，不扩散为多份文档的说明，也不顺带统一无关文风或扩展产品设计。
- 本 Skill 不自动调用数据或 Android Skill；只有当前请求同时包含那些范围时才组合。
