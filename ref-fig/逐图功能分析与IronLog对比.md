# 参考截图逐图功能分析与 IronLog 对比

> 分析日期：2026-06-28  
> 范围：`ref-fig/` 中 15 张参考截图。  
> 对比基准：当前仓库文档与代码中可核对的 IronLog 本地单人版能力。  
> 证据限制：多张截图来自视频播放页，底部视频控件与字幕遮挡了部分内容；以下只分析截图中可见的功能，不假定截图外能力。

## IronLog 当前对比基线

当前 IronLog 是 Android-first、本地优先、无账号、无服务器的单人训练日志。已实现训练创建/编辑/复制/删除、逐组记录、休息秒、计划/模板、按模板训练、动作库与动作详情、个人动作统计、实际训练月历、本地资料、主题选择基础 token、WebDAV 手动同步与备份。

当前明确缺口：CalendarPage 只显示实际训练记录，不渲染计划条目，也没有在日历格内直接显示训练部位；没有按周/月/年组织的统计页、年度训练报告、身体围度历史、体脂历史、单动作多指标趋势图、动作肌群可视化、RM 计算与持久化成绩记录、可生成图片的分享海报、多人只读/协作权限模型。

## 逐图分析

### 1. `微信图片_20260628223403_152_566.jpg`

**可见功能**：训练日历页，顶部有“日历 / 统计 / 年度”分段；下方按部位筛选，如全部、胸部、背部、肩部等，并显示距离最近训练的天数或“今天”。月历格内直接展示部位标签，标签用不同颜色区分胸、背、肩、臀腿、核心、手臂等；支持回到今天和切换月份。

**功能价值**：用户不用点开日期就能知道每一天练了哪些部位，也能快速判断某个部位多久没练。部位筛选把“查看训练记录”和“安排恢复间隔”合并在一个入口。

**相比 IronLog 的优势**：IronLog 当前 CalendarPage 用彩色点表示当天训练，并在选中日期后显示训练摘要；它不在日历格内直接写出肌群/模板标签，也没有按部位筛选和部位距今天数提示。参考图的信息密度和恢复决策辅助明显更强。正常训练场景下一天通常只采用一个计划/模板，日历格内直接展示训练部位比只显示彩色点更符合用户判断恢复和回顾的习惯。

**IronLog 的优势**：IronLog 的计划/模板关联、训练详情跳转和 WebDAV 本地分片链路更清晰；它避免把日历做成只依赖视觉标签的单页状态，数据可同步、可复制训练、可离线使用。

**可借鉴点**：IronLog 的日历页应全面向该方向看齐：日历单元格应增高，优先显示当天训练部位/模板短标签，而不是只显示点状标记；顶部保留“日历 / 统计 / 年度”一类子 tab，并提供部位筛选与“距上次训练 N 天/今天”的提示。若一天确有多次训练，按主要模板或训练部位显示 2-3 个标签，超出再折叠为 `+N`。

### 2. `微信图片_20260628223404_153_566.jpg`

**可见功能**：年度报告页。顶部展示年份、用户头像、最长连续训练、年度总容量，并用“约 355 台 Model S”做趣味类比。中段有人体肌群热力图、PR 对比列表、按月锻炼时间柱状图、年度训练日打卡热力图，以及训练/休息天数汇总。

**功能价值**：把训练数据包装成年度复盘，适合自我激励和分享。PR 对比和肌群热图能帮助用户发现训练重心和年度进步。

**相比 IronLog 的优势**：IronLog 目前只有首页本月统计、最近训练趋势、动作详情中的个人统计，以及训练列表/月历；没有年度报告、打卡热力图、跨年 PR 对比、年度肌群热力图和趣味类比。

**IronLog 的优势**：IronLog 当前不使用账号和会员能力，年度统计如果实现可以完全本地派生，不需要上传隐私训练数据。其 WorkoutDoc 聚合结构也适合本地计算总容量、训练天数和动作 PR。

**可借鉴点**：可以规划“年度复盘”作为只读派生页面，不新增持久化统计快照。第一版建议只做训练天数、总容量、最长连续、肌群分布、Top PR；趣味类比要谨慎，避免夸张或不可解释的换算。

### 3. `微信图片_20260628223405_154_566.jpg`

**可见功能**：深色主题统计页，支持周/月/年切换。顶部是年度肌群图，下面有组数对比、锻炼时间对比、容量曲线等模块；图表对比 2022 与 2023，并用“增加了”“👍”等文案表达变化。

**功能价值**：强调跨周期对比和趋势，而不是只显示单期总数。深色模式降低夜间查看压力，也使荧光色图表更突出。

**相比 IronLog 的优势**：IronLog 有 5 套主题定义和主题选择，但全页面语义色彩迁移仍在推进；统计图表只在首页有小型容量趋势，动作详情是统计卡片和历史组列表，没有周/月/年统一统计页，也没有上期/去年对比。

**IronLog 的优势**：IronLog 的主题系统按 token 设计，未来做深色主题时有更干净的落点；当前统计口径在 core/service 中集中，避免页面重复计算。

**可借鉴点**：统计页应按“周/月/年”组织统一入口，并把“对比上周期”作为默认阅读方式。它可以作为第 1 张日历页顶部的“统计”子 tab，而不是另起一个互不关联的主入口：同一个训练日历模块下，用户可在“日历”看具体日期，在“统计”看周/月/年复盘，在“年度”看年度报告。实现时应先补 core 层派生函数，再接图表，避免页面层散落计算。

### 4. `微信图片_20260628223406_155_566.jpg`

**可见功能**：动作详情页的“历史”tab。动作标题为 Leg Extension (Machine)，有“关于 / 历史 / 图表 / 记录”tab。历史卡片展示某次训练时间、执行的组、重量次数和估算 1RM，并用奖杯标签标记“重量 / 1RM / Vol.”等记录。

**功能价值**：用户查看某个动作时可以直接看到最近训练和 PR 标记，明确“这次是否刷新了重量、1RM 或容量记录”。

**相比 IronLog 的优势**：IronLog 动作详情有历史组记录和个人统计，但没有 tab 化分区，也没有估算 1RM、单组 PR 标签或“本次刷新何种记录”的视觉反馈。

**IronLog 的优势**：IronLog 已按动作记录类型区分 strength、cardio、reps_only、static_hold，并用历史 exerciseType 快照解释统计，避免后续动作类型变更污染历史。参考图只展示负重动作视角。

**可借鉴点**：可以在动作详情历史组上增加“本动作个人最佳”标记，但第一版建议只标记实际记录值，如最大重量、最大容量、最大次数，不急于引入 1RM 估算。

### 5. `微信图片_20260628223406_156_566.jpg`

**可见功能**：动作“DETAILS”页。展示主目标肌群 Glutes、次要肌群 Quads、小肌肉示意图、器械 BARBELL、器械图片、动作难度 Medium、添加到每次训练的收藏/固定入口、个人备注、英文动作描述，包括起始姿势、执行和注意事项。

**功能价值**：把“这个动作练哪里、用什么器械、难度如何、怎么做、个人备注”集中在动作百科页中，对新手友好。

**相比 IronLog 的优势**：IronLog 已有主/次目标肌群、动作要领和自定义动作备注式描述，但没有动作肌群可视化、器械字段、器械图片、动作难度、视频/GIF 或“加入每次训练”的固定动作入口。

**IronLog 的优势**：IronLog 的目标肌群是稳定选项 ID，而不是自由文本，这天然适合映射到人体肌群图。主目标肌群可以用深色高亮，次要目标肌群用浅色高亮，比参考图只显示单个 primary/secondary 更细致。自定义动作编辑复用统一表单，字段链路更稳定。

**可借鉴点**：媒体内容可以先忽略，但肌群可视化值得优先学习。开源肌群 SVG/PNG 资源应不难找到；更推荐把人体图作为本地静态资产，按 `primaryMuscleGroupIds` / `secondaryMuscleGroupIds` 着色渲染。短期可补“器械/难度”纯文本字段，视频/GIF 和器械图片后置。

### 6. `微信图片_20260628223407_157_566.jpg`

**可见功能**：同一动作详情页顶部展示动作视频/GIF，画面是杠铃深蹲演示；下方仍是目标肌群、器械、难度、收藏、备注和描述。

**功能价值**：动作视频比纯文字更容易理解动作路径和姿势，尤其适合新动作学习。

**相比 IronLog 的优势**：IronLog 当前不嵌入外链视频、GIF 或远端图片。参考图在动作教学方面更直观，但本轮真正值得吸收的是它把视觉素材放在动作详情首屏，强化“练哪里、怎么做”的即时理解。

**IronLog 的优势**：不依赖视频媒体意味着离线体积小、版权风险低、同步更简单。目标肌群选项 ID 可直接驱动肌群图高亮，不需要为每个动作寻找独立演示视频。

**可借鉴点**：先做肌群可视化，不把视频/GIF 作为动作详情增强的前置条件。若未来做媒体，应优先支持“用户自有本地媒体引用”或“可选资源包”，而不是默认远端视频。

### 7. `微信图片_20260628223408_158_566.jpg`

**可见功能**：动作“记录”tab。展示个人记录：预估 1RM、最大总重、最大重量；有“查看纪录历史”按钮；下方按名次列出多条记录，每条包含执行范围、日期和估算值。

**功能价值**：把动作 PR 从普通历史中抽出来，形成排行榜式记录。用户可以看到自己的第 1 到第 N 名表现，而不是只看最近训练。

**相比 IronLog 的优势**：IronLog 动作详情只显示单次最大重量、单次最大容量等聚合值和最近历史组；没有 PR 排行榜、记录历史按钮，也没有估算 1RM。

**IronLog 的优势**：IronLog 当前统计定义更保守，避免把估算指标当成事实。对于 cardio、自重、静力训练也有对应最佳指标，而不是只围绕杠铃动作。

**可借鉴点**：可以添加“个人记录”区，先支持真实记录排行榜：最大重量、最大容量、最大次数、最长时长、最快速度等。1RM 可以作为可选高级指标，需要公式选择和免责声明。

### 8. `微信图片_20260628223409_159_566.jpg`

**可见功能**：动作“图表”tab。展示多个趋势图：最佳组约 1RM、总重量、最佳组重量次数等；每个图表上出现“使用 PRO 解锁图表”提示。

**功能价值**：趋势图用于判断长期进步或平台期，同时通过 PRO 锁定形成商业转化。

**相比 IronLog 的优势**：IronLog 没有单动作多指标趋势图，也没有按动作维度的折线趋势。参考图的趋势分析入口更完整。

**IronLog 的优势**：IronLog 开源单人版没有会员锁定；如果实现趋势图，用户本地数据即可完整查看，不需要付费或上传。

**可借鉴点**：单动作趋势图值得做，但应避免 PRO 式锁定。第一版可在动作详情增加一个“趋势”折叠区，基于本地历史绘制最大重量/容量/次数/时长。

### 9. `微信图片_20260628223410_160_566.jpg`

**可见功能**：个人页/我的页。顶部头像、昵称 Chris、性别图标、永久 PRO 标识、训练 ID。列表入口包括分享训练、偏好设置、反馈中心、身体数据、教练记、公众号、数据备份、小工具、多设备登录、协议/账号相关。底部导航含训练、动作、训练/饮食、历史、我的。

**功能价值**：个人页是账户、设置、备份、工具和商业功能的总入口，适合复杂产品生态。它也说明复杂应用不能把所有配置都塞进“个人资料”表单，设置、数据、同步、工具和账号/权限应有分区入口。

**相比 IronLog 的优势**：参考图有更多生态入口：反馈、教练、公众号、小工具、多设备登录、账号协议、PRO。IronLog 当前 ProfilePage 更克制，只包含本地资料、头像、训练重量单位、主题和数据同步与备份入口。

**IronLog 的优势**：IronLog 当前不需要账号、登录、JWT 或服务器；WebDAV 端点配置不进入同步 JSON，密码隔离。这是当前本地单人版的隐私和部署优势。

**可借鉴点**：IronLog 现在“我的”页已经出现配置项不够直觉的问题，例如主题设置与个人数据没有直接关系，理应从个人资料中隔离出来。采用多入口是合理的：个人资料、应用设置、数据同步与备份、小工具、身体数据、分享/导出应分区。虽然当前是本地单人版，未来若准备上线或扩展协作，数据模型可以提前预留权限边界，避免后续迁移困难；即使不上线，也可以基于 WebDAV 目录或凭据权限探索“搭子”（只读）和“教练”（可读可写）等多人功能。该方向应作为远期权限/共享模型预留，不应倒逼当前引入账号后端。

### 10. `微信图片_20260628223548_161_566.jpg`

**可见功能**：单动作图表页，动作是深蹲。顶部展示容量记录、重量记录、1RM 预测记录；下方多条折线分别展示容量、组数、最大重量、1RM 预测，支持年份切换、上一年、下一年、全部。

**功能价值**：这是比第 8 张更完整的单动作趋势面板，将多个指标叠在一个时间轴上，便于理解训练量和强度是否同步上升。

**相比 IronLog 的优势**：IronLog 没有动作级年度趋势、多指标联动或年份切换。当前动作详情统计偏“当前摘要”，不是“长期分析”。

**IronLog 的优势**：IronLog 已有本地 WorkoutDoc 聚合和历史分片，理论上可以按动作稳定计算这些曲线，不需要新增服务端索引。

**可借鉴点**：适合列入动作详情二期：按动作生成容量、组数、最大重量和次数趋势。实现必须复用 core 统计口径，且要处理不同记录类型，不应只服务 strength。

### 11. `微信图片_20260628223549_162_566.jpg`

**可见功能**：训练完成后的分享图生成弹层。背景是训练报告卡片，包含日期、用户、肌群图、总量、距离、动作和组数据；底部有“更多样式”、微信分享、相册/图片保存、下载，以及取消。

**功能价值**：训练后即时生成可传播的图片，比纯文本分享更适合社交平台，也能增强完成感。

**相比 IronLog 的优势**：IronLog 当前 `WorkoutDetailPage` 支持系统分享或复制文本，并有训练分享数据预览；但没有多样式分享图、保存图片、下载图片或社交平台样式适配。

**IronLog 的优势**：IronLog 分享文本不依赖图片生成和平台授权，简单可靠；本地数据不必上传到服务端渲染。

**可借鉴点**：可以新增“本地生成分享图”作为独立功能。必须明确只在本机 canvas/DOM 渲染，不上传训练数据；并提供不含个人头像/昵称的隐私样式。

### 12. `微信图片_20260628223550_163_566.jpg`

**可见功能**：统计页的周视图。顶部在“历史 / 统计”间切换，周/月/年分段选择；时间范围为 2022-11-28 至 12-04；显示本周肌群热力图、组数对比柱状图，并与上周比较，给出“本周训练次数总计 5 次”“-3 次，减少了”等结论。

**功能价值**：以周为单位回答“这周练得够不够、练了哪里、比上周少了什么”。对短周期训练调整很有用。

**相比 IronLog 的优势**：IronLog 当前没有周统计页，也没有上周对比、肌群热力图和训练次数差异结论。HomePage 只有今日计划、补训建议、近期训练和本月概览。

**IronLog 的优势**：IronLog 已有 `getCalendar` 可生成计划完成状态，未来周统计可以同时对比“计划应练”和“实际完成”，这是参考图未显示的优势方向。

**可借鉴点**：优先级高。建议实现“周回顾”卡片：训练次数、总组数、总容量、肌群分布、与上周差值。它比年度报告更接近日常使用。

### 13. `微信图片_20260628223551_164_566.jpg`

**可见功能**：身体数据页的数据视图。人体轮廓图上标注脖子、肩宽、胸围、腰围、臀部、大腿、小腿等围度；下方显示体重和体脂率记录日期与数值。顶部可在“数据 / 图表”间切换。

**功能价值**：把训练日志和身体变化绑定，解决“训练表现提升”和“体型变化”之间的追踪问题。

**相比 IronLog 的优势**：IronLog 个人资料目前只有身高、体重、性别、出生日期等单值资料，没有体脂、围度、左右侧围度、记录日期或身体数据历史。全部写进 ProfileDoc 的单值形式不适合表达“变化”。

**IronLog 的优势**：IronLog 当前数据模型较简单，不会把健康/体测数据与训练处方混在一起；若扩展身体数据，可以作为独立文档分片，保持训练主链路稳定。

**可借鉴点**：身体数据应隔离成单独模块，定义独立 `BodyMetricDoc` 或按月分片的身体数据文档，支持体重、体脂和围度时间序列，并提供变化统计、趋势图和最近记录。ProfileDoc 只保留当前展示所需的少量资料或引用，不应承载身体历史。

### 14. `微信图片_20260628223552_165_566.jpg`

**可见功能**：身体数据图表视图。左侧可以选择体重、体脂、脖围、臀围、臂围、小腿、肩宽、胸围、腰围、腿围、小臂等指标；右侧展示体重 kg 的折线图；顶部可按日/周/月/年切换。

**功能价值**：比第 13 张的当前值视图更适合看变化趋势。指标列表常驻，能快速切换不同身体维度。

**相比 IronLog 的优势**：IronLog 没有身体数据趋势图，也没有多指标筛选和时间粒度切换。

**IronLog 的优势**：如果 IronLog 以后实现，可利用本地 JSON 分片和 WebDAV 同步，避免身体隐私数据进入第三方账号体系。

**可借鉴点**：身体数据模块应同时设计“当前值人体图”和“趋势图”。移动端要避免左侧指标列表压缩图表，可考虑横向 chips 或底部 sheet。

### 15. `微信图片_20260628223552_166_566.jpg`

**可见功能**：5RM/强度测试或 RM 计算工具。问题是“您最多可以用多少的重量差不多能做 5 次的深蹲（5RM）？”用户输入杠铃+片重量，支持 kg/lbs 切换，并可设置拥有的杠铃片和哑铃重量。上方有不同重量选项或动作图标，中央显示百分比。

**功能价值**：RM 计算是力量训练日志的必要能力，用于把不同重量、次数和主观强度的训练组换算到可比较的能力指标。IronLog 额外记录 RPE，因此可以用“重量 + 次数 + RPE/RIR”更全面、实时地估算 RM，而不只依赖重量和次数。

**相比 IronLog 的优势**：IronLog 当前支持重量单位、训练历史默认值、逐组记录和 RPE，但没有 RM 计算器、公式对比、器械库存配置，也没有把训练结束后的最佳组自动沉淀为动作个人记录。

**IronLog 的优势**：IronLog 已经在 WorkoutSetDoc 中保存 RPE、重量、次数和单位，数据基础比只记录重量次数的应用更适合做 RM 估算。现有动作详情的实时计算逻辑也有价值，可以作为持久化记录的校验和重建来源。

**可借鉴点**：RM 计算器既可以作为“小工具”独立使用，也可以在每次训练结束后，根据每个动作的最大重量、次数和 RPE 自动更新个人动作记录。动作库中的成绩记录应持久化，但现有实时计算逻辑不应删除；应保留“重置/重新计算”按钮，用实时扫描结果重建持久化记录，避免同步或合并异常导致记录漂移。主流 RM 公式应分别保存结果字段，例如 Epley、Brzycki、Lombardi、O'Conner、Mayhew、Wathan、Lander，以及基于 RPE/RIR 修正的估算字段；每个公式的结果独立同步更新。还应有独立说明页介绍 RM 计算公式及适配场景、最大心率公式、RPE 量表：力量训练按“还能做几次”解释，有氧训练按主观感受和对应心率分区解释。

## 横向结论

### 参考产品更强的方向

1. **统计复盘更完整**：周/月/年/年度报告、上期对比、年度打卡、PR 对比和肌群热图都比 IronLog 当前更成熟。
2. **动作详情更像百科和分析中心**：肌群可视化、器械、难度、个人备注、PR 排行榜、多趋势图让动作页承载更多决策信息。
3. **身体数据闭环更完整**：围度、体脂、体重和趋势图补足了训练表现之外的身体变化。
4. **分享传播更强**：可生成训练分享图，并提供多样式、保存和社交平台入口。
5. **RM 与小工具更完整**：RM 计算、配重和器械库存配置能提升实际训练记录、复盘和能力比较的准确性。

### IronLog 当前更强或更符合定位的方向

1. **本地优先和隐私边界清晰**：无账号、无服务器、WebDAV 仅作文件同步/备份，适合开源单人版。
2. **数据链路更可控**：WorkoutDoc 聚合、tombstone、migration、DocumentStore 和 WebDAV 分片链路已成体系。
3. **训练记录基础更稳**：休息秒、草稿恢复、复制训练、模板关联、动作类型快照和单位换算都有明确契约。
4. **不会用会员锁定本地数据**：参考图中 PRO 图表是商业优势，但不适合 IronLog 的开源单人版定位。
5. **适合渐进扩展**：很多参考能力可以作为本地派生视图或本地持久化记录，不必立刻引入后端或账号。

## 建议优先级

### P1：高收益、低侵入

- CalendarPage 向第 1 张图看齐：增加日历子 tab、部位/模板筛选、训练部位短标签，并提高日历单元格高度。
- 在日历模块的“统计”子 tab 新增周/月/年统计：训练次数、总组数、总容量、肌群分布、与上周期差值。
- 动作详情增加肌群可视化，基于主/次目标肌群 ID 用深浅色区分。
- 动作详情增加“个人记录”区，并纳入 RM 估算结果；保留实时计算作为校验/重建来源。
- 分享页增加本地生成图片的隐私样式，保留纯文本分享作为兜底。

### P2：中等投入

- 动作详情增加趋势图：最大重量、容量、组数、次数/时长，按动作类型适配。
- 年度复盘页：训练天数、总容量、最长连续、肌群分布、年度 PR。
- 身体数据独立模块：体重、体脂、围度时间序列、变化统计和趋势图。
- RM 工具独立页面：支持多公式结果、RPE/RIR 修正、最大心率公式、RPE 量表说明、器械/配重配置。

### P3：谨慎推进

- WebDAV 多人共享模型：可先做数据模型预留，区分只读“搭子”和可读写“教练”，但不改变当前本地单人版运行目标。

### P4：目前不考虑

- 账号体系、会员能力：与当前开源本地单人版战略冲突，不应作为近期实现路径。
- 动作视频/GIF 和器械图片：需要版权、资源体积和同步策略；肌群图不应被这些媒体能力阻塞。

## 额外功能思考

参考图中没有直接出现，但 IronLog 值得考虑“日期/时间段备注”模块。用户可能需要记录某个训练环境或生活方式变化，例如从某天开始跑步通勤、某段时间更换了器械品牌、某个阶段睡眠/工作压力显著变化、某家健身房器械角度导致体感重量不同。如果这些上下文不进入数据，未来复盘容量、RM、身体数据或跑步表现变化时会缺少解释。

建议设计独立的 `TimelineNoteDoc` 或类似文档：支持单日备注、起止日期备注、关联动作/模板/训练可选、标签和正文。它应参与本地 JSON 分片与 WebDAV 同步，但不直接改写训练记录；统计页和动作趋势页可以按时间范围显示这些备注标记，帮助解释曲线变化。

## 对文档/实现的提醒

- 若新增身体数据，先更新字段契约矩阵，建议用独立 `BodyMetricDoc`，不要扩展 ProfileDoc 为历史表。
- 若新增 RM 和动作成绩记录，建议定义独立持久化记录文档或动作记录分片；保留实时计算路径，并提供手动重置/重算入口。
- 若新增趋势和年度统计，优先放在 core/service 派生层；只有 RM/PR 这类用户期望保留的个人成绩记录需要持久化。
- 若新增日历部位筛选，必须区分“过滤/仅显示”和“高亮/排序”，避免违反当前项目语义规则。
- 若新增分享图，必须保证本地生成、可隐藏个人资料、WebDAV 不自动上传分享产物。
- 若新增动作肌群可视化，优先使用开源或自制人体肌群图资产，并由稳定肌群 ID 驱动深浅色渲染；若新增动作视频/GIF，才需要进一步解决版权来源、离线可用性、资源路径和同步策略。
